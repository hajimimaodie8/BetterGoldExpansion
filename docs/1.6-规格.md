## 二、已落地的两处修正（批 3）

### 2.1 §5.2 创造页横幅的 Z 深度 bug

**现象**（作者原话）：鼠标移到横幅**下方**的物品时，那个字（tooltip / 名字）被横幅盖住。

**根因（源码级，两条叠加）**

1. **不是"z 不够"，是"画得太晚"**：`AbstractContainerScreen#render` 第 141 行
   `RenderSystem.disableDepthTest()` 把**深度测试整个关掉** ⇒ z 参数不参与遮挡判定，
   只有**绘制顺序**说话。所以「改 z 深度」这条方向**物理上无效**（需求的验收也不许靠隐藏/降透明度绕过）。
2. 旧落点 `ScreenEvent.Render.Post` 由 `ClientHooks.java:429-430` 在
   `screen.renderWithTooltip(...)`（tooltip 是**最后**一步，`Screen.java:111-117`）**整段之后**才发
   ⇒ 横幅必然压在 tooltip 之上。参考实现（航空学）注入的是 `render` 的 TAIL（= tooltip 之前），
   所以它没有这个 bug —— **旧注释里那句"两者时序等价"是错的**。

**改动**

| 文件 | 改什么 |
|---|---|
| `client/CreativeSectionBanners.java` | 事件入口 `ScreenEvent.Render.Post` → **`ContainerScreenEvent.Render.Foreground`**（`renderLabels` 之后、tooltip 之前；其 javadoc 原文就是 "after … foreground layer … **before rendering the tooltips**"）；方法名 `onScreenRender` → `onContainerScreenForeground`；取界面改用 `event.getContainerScreen()` |
| 同上 | **坐标改容器相对**：该事件在 `pose().translate(leftPos, topPos, 0)` **之内**发出（`AbstractContainerScreen:142-143`，push 后未 pop）⇒ `int left = ITEM_AREA_X;` / `int top = ITEM_AREA_Y;`（不再加 `guiLeft/guiTop`） |
| 同上 | 删掉已无调用点的 `guiLeft(...)` / `guiTop(...)` / `readInt(...)` 三个反射助手（**整块删除、不是注释掉**，旧口径写进类 javadoc 留档） |

**验收（B 级已完成 / A 级待办）**：静态关卡 `[bg16-banner-foreground]` / `[bg16-banner-relative-coords]` /
`[bg16-banner-old-event]` / `[bg16-banner-no-absolute-coords]` 全绿 + 扰动实测逐条命中（`docs/bg16-证据/01`）。
**A 级待办**：`runClient` 里逐个悬停横幅下方的物品，确认名字与 tooltip 都在最上层、横幅仍清晰可见。

### 2.2 §5.1 安抚 buff 对玩家生效

**口径**（作者原话）：「安抚 Buff 对玩家起效为**禁止移动** + **无法使用左右键**」。

**实现（全部运行时判定，`player.hasEffect(AllEffects.SOOTHE)` 是唯一判据）**

| 落点 | 做法 |
|---|---|
| 禁止移动 / 禁止跳跃 | `PlayerTickEvent.Post`（仅服务端）：安抚在身 ⇒ 给 `MOVEMENT_SPEED` 与 `JUMP_STRENGTH` 各挂一个 **`ADD_MULTIPLIED_TOTAL` −1.0**（= ×0）的 **transient** 修饰符；不在身 ⇒ `removeModifier`。两条属性都是 `setSyncable(true)`（`Attributes.java:80-81,114-116`）⇒ **客户端读到的就是 0**，按键不产生输入、无需网络包，也不会有"橡皮筋" |
| 左右键全部用途 | 7 个处理器：`AttackEntityEvent`（攻击）/ `BlockEvent.BreakEvent`（破坏）/ `PlayerInteractEvent.{LeftClickBlock, RightClickBlock, RightClickItem, EntityInteract, EntityInteractSpecific}`，一律 `setCanceled(true)`（`LeftClickBlock` 没有 `setCancellationResult`，只 cancel） |

**★ 可逆性（本轮第一优先级）**：**零持久状态** ——
不写 NBT、不进 `SootheState`（非 `Mob` 本来就直接 return，玩家的 `restore/clear` 天然是空操作）、
修饰符是 transient（不落盘），而且每 tick **双向**判定。
⇒ 自然到期 / 牛奶 / 指令 / 死亡 / 退服 / 重启，任何一条路径下一 tick 都恢复原状，
**结构上不可能出现"被安抚过的玩家永久不能动"**（这正是 `SootheState` 那段血泪注释的教训）。
关卡用 `[bg16-soothe-state-untouched]` 把"既有生物机制一个字没动"钉成**恰好三处守卫**的反向不变量。

**验收（B 级已完成 / A 级待办）**：静态关卡 + 扰动 12 例（`docs/bg16-证据/01`）。
**A 级待办**：真人玩家上施加安抚 → 试走动/跳跃/左右键各自无效 → 到期后确认能动能用键，
**反复 10 次**（需求 §6.3 明写）。

## 三、动手前已定好的口径（批 1 / 批 2 / §3.8，实现时照此）

1. **两族 Spec 一个数值字段都不覆盖**：`MetalFamily.Spec` 默认值（4096 / 24 / 14F / 4.5F /
   护甲 5·8·10·5 / 耐久 962·1110·1184·814 / 韧性 6F / 击退 0.15F）与 1.6 规格**逐项相同**，
   逐件伤害/攻速也由 `1 + 4.5 + 每武器常量` 自动得出（剑 10/1.8、斧 12/1.2、镐 8/1.4、锹 8.5/1.2、锄 7/4.2、刀 7.5/2.2）
   —— 这组反算是【读源码 + 算术】，**必须实机复核**。
2. **重锤 ×1.2 与三叉戟投掷 15 不用新写**：`MetalEvents.onMaceFinalDamage`（按 `MaceItem` 判）与
   `onTridentThrownDamage`（按族 `isWeapon` 判）已是**全局**规则，新金属自动继承。
3. **免疫仙人掌（两处落点，都不需要 Mixin；源码取证见 `docs/bg16-证据/05`）**：
   - 物品形式 → `EntityInvulnerabilityCheckEvent`（`ItemEntity#hurt` 第一句就问 `isInvulnerableTo`）；
   - 装备耐久 → `ArmorHurtEvent`（原版循环已被 NeoForge 废掉，盔甲耐久唯一执行点）。
4. **两个 buff 的数值**：寄生 = 等级 1/2/3 ⇒ 每秒 1/2/3 点 `cactus` 伤害、时长 **320 tick（16 秒）**、
   叠加无上限、每次伤害结算时 36% 概率给施加者回 `等级` 点血（施加者 UUID 记在目标持久数据）；
   幽咆 = 每秒以目标方块坐标 ±1（3×3×3，含自己）造成 `等级` 点 `sonic_boom` 伤害 +
   `SONIC_BOOM` 粒子，时长 **120 tick（6 秒）**，叠加提升等级。
5. **盔甲 25% / 全套 100%**：减免 `damage × (1 − 0.25 × 件数)`、反制 `min(1, 0.25 × 件数)`，
   与既有靛海金 `counterChance` 同构（照抄，不另造口径）。
6. **建材 trait**：树棘金 = 四动作 ⇒ 对触发者 1.0 点 `cactus`；幽咆金 = 四动作 ⇒
   方块中心 3×3×3 全部生物 3.0 点 `sonic_boom` + 粒子；冷却复用既有 10 tick 语义、
   **每族独立键**；**不清除掉落物**（= 新代码里不许出现任何 `ItemEntity` 摧毁逻辑，写成负向断言）。

   判据 = 方块 ∈ `#minecraft:leaves` ∪ `minecraft:vine` 且工具 ∈ 本模组全部族器具/五类武器；
   概率 `p = 0.06 + 0.06 × 时运等级`；另加 `Compostable(0.65f)`。

   否则**静默不生效**（关卡要断言这一条）。

## 7.3 本轮的三条探针工程教训（都写进 `mcmod_experience.md`）

1. **原版 `FakePlayer` 三层静默免伤**：`isInvulnerableTo` 恒 `true`、`spawnInvulnerableTime=60` 在空 `tick()` 下**永不递减**、`instabuild` 让 `ItemStack#hurtAndBreak` 空转 ⇒ 不逐条解除，任何 `hurt()` 路径的探针都会得到**假红/假绿**（本轮第一版 6 条红全部由此而来）。

`cactusImmune` 这一族旗标原先只覆盖「**家族索引命中**」的物品 —— 锭 / 粒 / 原料 / 升级模板 / 器具 / 五类武器 / 盔甲 / 建材
（这些都在 `MetalFamily.allItems` / `allBlocks` 里，注册完由 `MetalFamily.ensureIndex()` 写进 `BY_ITEM` / `BY_BLOCK`）。
而**核心材料**（`coreItem`：炽焰棒 / 巫毒羽毛 / 紫紫能晶尘 / 靛蓝海洋之心 / 紫颂樱花枝 / 金钱贝 / **闪耀藤条** / **集束回响碎片**）
是在 `MetalSpecialItems` / `AllItems` 里注册的，**不在任何族的 `allItems` 里**
⇒ `MetalFamily.of(核心材料) == null`（上一轮 A 级已实测并钉成断言，见 §6.3 第 1 条）
⇒ 那句 `family != null && family.cactusImmune` 对它们**恒为 false** ⇒ **闪耀藤条这类核心材料不免疫仙人掌**。

### 9.2.2 落点选择与理由

**落点 = 新增 `src/main/java/com/hjmmd_8/bettergold/mixin/CrossbowChargeDurationMixin.java`** ——
MixinExtras `@ModifyReturnValue`（`require = 1` **写死**、目标方法写**完整描述符**）注入那个 `static` 方法，
**只对本模组的弩**返回 `MetalCrossbowItem.chargeDuration(stack, shooter)`（基础 1.0 秒 = **20 tick**、快速装填每级 −0.25 秒），
其它一切物品**原样返回** `original`。登记在 `bettergold.mixins.json` 的 **`mixins`** 列表（= **双端**；**不在** `client` / `server`）。

> ⚠ **本轮踩到并修掉的一个静默坑（A 级抓到的，务必记住）**：Sponge Mixin 的配置**只认 `mixins` / `client` / `server` 三个列表键**，
> **没有 `common` 这个键**。第一版把类名写进 `"common": [...]` ⇒ **整个列表被静默忽略**：
> 编译全绿、`runData` 全绿、`required: true` 也**不报错**（列表为空 ⇒ 没有东西需要 apply），
> 而 A 级实测里 `CrossbowItem.getChargeDuration(本模组弩)` 仍然是 **25**、装载门槛仍是 25 tick。
> **正确键名 = `mixins`**（见 Mixin `MixinConfig` 的字段：`mixins` / `client` / `server`）。
> ⇒ **新增 mixin 后必须在能触发该路径的 `run*` 日志里 `grep` 到 `Mixing <Mixin类名> from ... into <目标类>` 那一行**才算"加载了"；
> 关卡也据此把"必须在 `mixins` 列表里、且不在 `client`/`server` 里"钉成断言（`bg16-crossbow-mixin-listed` / `-side`）。

**为什么选它（而不是"在弩类里重写装载判定"这条备选）**

1. **备选路压根没法干净照抄**：`CrossbowItem#tryLoadProjectiles(LivingEntity, ItemStack)` 是 **private static**、
   `getChargingSounds(ItemStack)` 是 **包私有**（`CrossbowItem.java:270-272`）⇒ 想重写 `releaseUsing` 就得连"抽弹 + 结束音效"一起复刻，
   而音效那条还牵 `EnchantmentEffectComponents.CROSSBOW_CHARGING_SOUNDS` 的取值链接。
2. **mixin 一处修好三处**：`getChargeDuration` 同时喂 **装载门槛** / **`onUseTick` 的装填音效阈值** / **客户端 `pull` 谓词**，
   走 mixin 时三者天然同步；重写 `releaseUsing` 只修门槛，音效阈值与动画会与门槛**分家**。
3. **侵入面更小**：mixin 只是"给一个 static 方法的返回值加一个 `instanceof` 守卫"，**没有一行业务逻辑被复制**；
   备选路要复制一小段原版逻辑 ⇒ **将来原版改这两行时我们会静默分叉**。
   （本 mixin 的另一面就是"分叉风险"本身：原版若改 `getChargeDuration` 的**签名或返回点**，
   `require = 1` + 完整描述符会**当场报错**，而不是静默失效 —— 这正是红线 7 要的形状。）

**放弃了什么**：① 上游修 bug（例如原版将来真给弩加"可覆写的蓄力入口"）我们不会自动受益，要删 mixin；
② 那个 `static` 方法现在是**第三方也能调**的公共 API，本模组只对**自己注册的物品**改语义（别人的弩拿到原值），
但如果某个第三方模组**用我们的弩**去问 `CrossbowItem.getChargeDuration`，它会拿到 20 —— 那是本裁定的**本意**，不是副作用。

### 10.1.3 依赖坐标与版本区间（**核实过，不是猜的**）

- Modrinth Maven 上有 `maven.modrinth:patchouli:1.21.1-93-neoforge`（POM 实测 `HTTP 200`，
  `groupId=maven.modrinth` / `artifactId=patchouli` / `version=1.21.1-93-neoforge`）。
- `versionRange="[1.21.1-93,)"` **只写下限**：Patchouli 自己的 mod 版本号是 `1.21.1-93-neoforge`
  （`${file.jarVersion}`），按 Maven 的 `ComparableVersion`，"1.21.1-93-neoforge" **大于** "1.21.1-93"
  （未知限定符排在 release 之后）⇒ 下限命中；写上界会让它每发一版就把本模组卡住。

## 10.2 口径：两种 optional 范式（**别混用**）

| | 农夫乐事（`fd` 包，1.4 起） | **Patchouli（本轮，`patchouli` 包）** |
|---|---|---|
| 口径 | **A · 总是注册、功能软依赖** | **B · 没装就不注册** |
| 物品 | 刀永远存在；FD 的类靠**反射**绕开（`FdItems.createKnife`） | **手册物品只在 Patchouli 加载时才 `register`**（`HandbookModule.register` 没装时返回 `null`） |
| 对类加载的要求 | 允许在字段初始化器里引用对方的类型（反射兜住） | **任何静态引用都会在类加载时炸** —— 引用**只许在方法体内、且在 `isLoaded(...)` 早退之后**（字段 / 构造器签名 / 静态初始化块里都不许有） |
| 触发依据 | 作者要"刀始终存在" | 作者原话「**没装手册进不去**」= 那一格**根本不存在**（不是"存在但打不开"） |

**构建形态（关键，别顺手加 localRuntime）**：

| 项 | 值 | 理由 |
|---|---|---|
| `gradle.properties` | `patchouli_version=1.21.1-93-neoforge` | 版本号只有一处真源 |
| `build.gradle` | `compileOnly "maven.modrinth:patchouli:${patchouli_version}"` | 编译期能写类型安全的调用 |
| `build.gradle` | **故意不加 `localRuntime`** | FD 加了 `localRuntime` ⇒ dev 环境**永远**装着它；Patchouli 若也加，**"没装"这一档就再也造不出来**（本轮两种环境的 A 级实测正是靠 `run/mods` 里放/拿 jar） |
