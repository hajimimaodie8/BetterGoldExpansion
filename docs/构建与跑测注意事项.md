# 构建与跑测注意事项（踩过的坑，2026-09 补充）

本文件记录 1.4 开发中真实踩过、且**会重复踩**的坑。做任何改动前先扫一眼。

## 一、判断构建成败：别被 PowerShell 骗了

- `.\gradlew.bat build ... 2>&1 | Tee-Object`（或任何把 stderr 合进管道的写法）会把 javac 打在 stderr 的
  `注: xxx 使用了已弃用 API` 之类提示，被 PowerShell 记成 **NativeCommandError**，于是 pwsh 报 `exit 1` —— 但
  **Gradle 的真实退出码是 0、构建是成功的**。
- 正确做法：把 stderr 单独重定向到文件（`2>build\x.err`），或直接看 Gradle 输出的 `BUILD SUCCESSFUL` / `BUILD FAILED`。
- 同理：`git push` 的进度信息也走 stderr，出现红色 `NativeCommandError` 不代表失败，看 `$LASTEXITCODE`。

## 二、run\ 目录是独占资源，必须串行

- 同时跑两个客户端（或客户端 + 服务端）会抢 `run\logs\latest.log`、`options.txt`、世界文件，典型症状是
  **卡在 100% 加载不动**、或日志被另一个进程删掉报 `Unable to delete file ... latest.log`。
- 另外 `run\saves\` 与 `run\world\` 的 `session.lock` 也要注意：重跑前先删。
- **杀进程要精准**：只杀游戏进程（命令行里含 `forgeclientdev` / `forgeserverdev`，或按 `serverRunVmArgs` 定位），
  不要 `Get-Process java | Stop-Process -Force` 一把梭 —— 那会连带杀掉 Gradle daemon，进而写坏配置缓存
  （症状：`Could not load compiled classes for build file ... from cache`，修法是 `gradlew --stop` + 删
  `.gradle/configuration-cache`）。
- 多个人（或多个子代理）协作时，**由协调方逐个发放 run\ 许可**，不要指望两边自己打招呼 —— 我们因此白跑过一轮。

## 三、临时探针的铁律

1. **绝不允许 `server.halt(...)`（或任何能关掉别人服务器/客户端的能力）进入生产代码**。曾经有一个临时探针
   在别人客户端进世界时触发 `halt`，直接把对方正在跑的集成服务器关掉，整轮验证作废。探针收尾必须**整块删除**
   （不是注释掉），并给出 grep 证据。
2. 需要自动退出时，用开关文件保护（例如 `run\xxx-probe.enabled` 存在才动作），收尾时开关文件一起删。
3. 探针控制台输出中文在 Windows 下会按 GBK 写出，重定向后按 UTF-8 读会乱码 → 探针把中文转成 `\uXXXX`
   打印，或用 `cmd /c "..." > file` 原始字节重定向，不要经过 PowerShell 转码。
4. **探针关服只能调一次 `halt(false)`**：先 `stopServer()` 再 `halt(false)` 会走两遍关闭流程，
   日志停在存盘循环里不再推进（现象像卡死/存不住盘，实际是重复关闭）。正确做法是**只调用一次 `halt(false)`**，
   随后原版流程自己完成 "Stopping server → 存盘 → 卸载 config"。
5. **测「范围内实体」类特性之前，必须先把测试区块 forceload 掉，并等几 tick 再取样**（1.4 三把金属刀
   修复时踩到，代价是一轮假阴性）。
   - **现象**：在**没有玩家**的专用服务器里，探针用 `level.setBlockAndUpdate(...)` 刚碰开的区块
     **不是 ticking 区块**；此时 `Level.getEntitiesOfClass(...)` / 任何 AABB 查询**看不见**刚生成的实体 ——
     严重到连「目标自己」（那个刚刚 `addFreshEntity` 并成功挨了一刀的僵尸）都查不到。
     于是 `MetalEvents.thunderStrike` 的 3×3 循环拿到空列表（内部计数 `victims=0`），
     雷实体也查不到，看起来像「结雷金的落雷/3×3/颤栗全都坏了」——**实际是测量方法错了，模组没坏**。
   - **根因（源码级，neoforge sources）**：`EntitySectionStorage.getEntities(test, aabb, consumer)`
     走的是 `forEachAccessibleNonEmptySection(...)`，只遍历 **`Visibility.isAccessible()`** 的
     entity section；`Visibility.fromFullChunkStatus`：`≥ ENTITY_TICKING → TICKING(true,true)`、
     `≥ FULL → TRACKED(accessible=true)`、否则 `HIDDEN(false,false)`。
     也就是说「区块加载了但没到 FULL 档」的实体对 AABB 查询是**不可见**的。
     注意 `LevelEntityGetterAdapter` 里按 **id/UUID** 查（`visibleEntityStorage`）和按 **AABB** 查
     （`sectionStorage`）走的是两套存储，所以不要用「id 查得到」推断「AABB 查得到」。
   - **正确做法**：探针里对每个测试区块 `level.setChunkForced(chunkX, chunkZ, true)`
     （等价 `/forceload add`），**等几 tick**（本次等到第 100 tick，用 `ServerTickEvent.Post` 触发，
     不要在 `ServerStartedEvent` 里就地取样），再生成实体/取样；用
     `level.getEntities().getAll()`（tracked 实体扫描）与 AABB 查询**互相印证**，并在日志里打印
     `entityLookupSeesTarget` / 查询命中数，避免再次把假阴性当成 bug。
   - **收尾**：探针结束时把临时 forceload 的区块 `setChunkForced(..., false)` **撤销**
     （并核对 `ServerLevel#getForcedChunks()` 计数回到 0），否则 dev 世界会一直带着一堆 forced chunks。
   - **可信度**：这条是**源码（`EntitySectionStorage` / `Visibility` / `LevelEntityGetterAdapter`）
     与实测双向确认**——forceload 之后同一段代码 `victims=3`、雷实体 1 个、3×3 每人 −5.9 HP
     （裸 6.0，僵尸 2 点护甲按 `CombatRules` 折算）、颤栗 320t 全部正常。

## 四、文件与编码

- 一律**无 BOM**（`Set-Content -Encoding UTF8` 会写 BOM；JSON 与 .java 都可能因此出问题）。用编辑工具，
  或 `[System.IO.File]::WriteAllText(path, text, (New-Object System.Text.UTF8Encoding($false)))`。
- **不要用 `Get-Content`/`Set-Content` 做文本替换**：会把中文注释变成乱码（本仓库中过两次，只能靠 git 恢复）。
  必须用 PowerShell 时走 `ReadAllText/WriteAllText` + 显式 UTF-8。
- 文件行尾多为 CRLF，PowerShell 里用 `` "`r`n" `` 拼多行锚点；不确定时优先用编辑工具而不是字符串替换。
- **删代码块要按标记+锚点成对定位**，别用行数算术（我曾多切 4 行，切出多余右括号导致构建失败）。

## 五、创造模式标签页相关（1.21.1 实测）

- `output.accept(ItemStack.EMPTY)` **不是被过滤，而是直接抛异常**：NeoForge 在
  `EventHooks.onCreativeModeTabBuildContents` 里对每个 stack 校验 `getCount() == 1`，而 EMPTY 的 count 是 0。
  想插空行必须绕开它 —— 我们的做法是用 `CreativeModeTab.Builder#withTabFactory` 造一个
  `SectionedCreativeTab`，覆写 `getDisplayItems()` 把空格子补回去（创造界面本来就只读 `getDisplayItems()`）。
- **GUI 贴图不能用 `blitSprite`**：1.21.1 的 GUI 图集只扫 `assets/<ns>/textures/gui/sprites/`，放在
  `gui/` 其它子目录的贴图 `getSprite` 查不到，会静默退化成 missing sprite（紫黑格、不报错）。
  要么放进 `gui/sprites/`，要么用 `graphics.blit(贴图, x, y, 0, 0F, 0F, w, h, texW, texH)`。
- 创造页排序：`withTabsBefore(X)` 的含义是「X 在本页之前」，整条链要锚在 `CreativeModeTabs.SPAWN_EGGS`
  之后才不会把原版页挤到第二页；不要锚 `HOTBAR/SEARCH/OP_BLOCKS/INVENTORY`（它们是 `DEFAULT_TABS`，
  被排除在排序图之外，边会把它们拉回图里）。

## 六、可信度要求

- **只读 JSON 不算验证**：我们有过一次"读了掉落表 JSON 里 chance=0.36 就宣称修好"的事故，实际那份表
  **根本没有被加载**（解析失败），玩家打半天不掉东西。任何数据文件都必须**让游戏真的加载它**，并留下日志证据。
- 汇报时把「实机验证过的数字」与「仅编译/仅读源码」明确分开，后者一律标注为未验证。
- **关卡的期望值不许读仓库外的「活页文档」**（2026-10-05 `bg-append` 轮实测）：`validate_metal_data.py` 原先
  直接读 `..\mod_experience\开工需求\*.md` 取"逐字文案的期望值" ⇒ 设计会话一改那份文档，**构建当场变红、
  且与代码无关**。现行口径：期望值一律来自仓库内的**冻结快照**
  （`tools\asset-generator\bgappend-requirements-snapshot\`，末尾有"搬运记录"表），细节见 `docs\1.6-规格.md` §17.3.1。
- **扰动实测要能区分"关卡漏了"与"扰动没生效"**：脚本必须显式报出"变更未生效"，并把 `exit` 与
  `hit_expected` 两列都打出来；`exit 2`（脚本自身出错）**一律当作用例坏了**，不算命中。三条陷阱
  （断言看的是调用点而非条件真假 / CRLF 下多行字面量匹配会静默不中 / 把 JSON 改成解析不了的形状）
  见 `mod_experience\ex\03-验证与证据.md` §3.11。
