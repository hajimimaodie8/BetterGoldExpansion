## 三、端到端挖掘计时的**原版常量**（为什么"首例 +0、其余 +5"）

| 事实 | 类名:行号 | 原文 |
|---|---|---|
| 挖掉一个方块后把延迟设回 5 | `net/minecraft/client/multiplayer/MultiPlayerGameMode.java:259` | `this.destroyDelay = 5;` |
| 这 5 tick 被整个吃掉（不累进度） | `MultiPlayerGameMode.java:212-214` | `if (this.destroyDelay > 0) { this.destroyDelay--; return true; }` |
| 它只在**按住攻击键**时递减 | `MultiPlayerGameMode.java:210` + `Minecraft.java:2047` | `continueAttack(...)` → `this.gameMode.continueDestroyBlock(pos, dir)` |

**⇒ 探针把原始 tick 数减去"首例 0 / 其余 5"得到"纯破坏进度 tick"**（公式写在探针 `progressTicks()` 的 javadoc 里）。
两个改前基线（runA / runA2）实测逐位相同：`12 / 60 / 21 / 82`，与"+0/+5"完全吻合。

## 四、边界（本轮**没有**动的另一条惩罚）

`Player.java:799-800` 的 `if (!this.onGround()) { f /= 5.0F; }` 是**另一条**规则（离地就减半再除以 5），
与 `SUBMERGED_MINING_SPEED` 无关。本需求 §9.3 只要求"无视水里挖掘惩罚"（那条属性），
所以探针把两个站位都做成 **脚踩实地（`onGround=true`）**，并且把 `onGround` 写成断言
（`attr_onground_*` / `mine_onground_*`）——否则会混进"离地 /5"，把 1.0 vs 0.2 的对照污染成"1.0 vs 0.04"。
**边界（未验证）**：在水里**悬空**（游着挖）时，上面那条 `/5` 仍然生效 —— 轮不到本轮的口径，未改、未验。
