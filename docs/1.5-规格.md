## 三、两个新 buff

### 3.1 沉淀 sediment（靛海金）

- **持续受窒息伤害**：1 级 = 2 点、2 级 = 3 点，即 **伤害 = 等级 + 1**。
  换成代码口径（与 1.4 `high_burn` 逐字同构）：`amplifier + 2` 点，每秒结算一次
  （`shouldApplyEffectTickThisTick` 里 `duration % 20 == 0`）。
- **降低目标 1% 移动速度**：是「每级 1%」还是「固定 1%」→ 第七节第 2 条（我方按**每级 1%** 实现）。
  ⚠ 实现坑：玩家基础移速是 **0.1**，用 `AttributeModifier.Operation.ADD_VALUE` 加 −0.01 实际是 **−10%**；
  要 1% 必须用 **`ADD_MULTIPLIED_TOTAL`**（配合 NeoForge 的等级曲线重载，
  和 1.4 `tremble` 用 `addAttributeModifier(..., amplifier -> ...)` 是同一套写法）。
- 无等级上限（器具每次命中 +1 级）。

### 3.2 安抚 soothe（幻惑金）

- 目标**暂时失去 AI**，无法做出任何行动 → `Mob.setNoAi(true)` + `setTarget(null)`。
- 需要一张**服务端状态表**（照 `VoodooAccumulator` 的写法：`Map<UUID, 原状态>`）来记录「原本的 NoAI 值 / 原本的目标」，
  在**到期、提前移除、目标死亡、实体离开世界、世界卸载**时还原并清表 —— 否则被安抚过的生物会永久变傻。
- 时长 1 秒（20 tick）；器具 16% 概率施加；盔甲每件 4% 反制。
  「重复施加是否延长时长 / 是否叠加」→ 第七节第 8 条（我方按**不叠加、时长取 max**实现）。

## 四、巫毒公式变更（1.5，**已定稿**）

### 4.1 旧公式（1.4 已发布，`voodooStoreRatio` 0.8 / `voodooReleasePerLevel` 0.8）

```
窗口内每次受到的伤害 × 0.8 累加为「存储伤害」
自然到期结算 = 存储伤害 × (1 + 0.8 × 效果等级)        // 1 级 ×1.8、2 级 ×2.6 …
```

### 4.2 作者原话与两种解读

作者原话：「把巫毒的效果改成以 buff 的等级 **+** 提取于 36% 点这期间所造成的伤害量造成百分比伤害」。
断句有歧义，两种读法：

| 解读 | 公式 | 结果 |
|---|---|---|
| **A（定稿）** | `窗口内伤害总量 × 36% + buff 等级` | 乘除先算、加减后算 |
| B（否决） | `(窗口内伤害总量 + buff 等级) × 36%` | 括号先算 |

作者 2026-09-30 裁定原话：**「就是字面意思，算乘除，再算加减」** → **采纳 A，否决 B**，歧义**已解决**。

### 4.3 最终公式（唯一实现处：`material/VoodooAccumulator#settleDamage`）

```
结算伤害 = 提取值 + 每级固定伤害 × 效果等级
        = (窗口内伤害总量 × 36%) + buff 等级
```

- `效果等级 = amplifier + 1`（与全模组口径一致）；伤害类型仍是 `damageSources().magic()`。
- 语义**不变**：只有效果**自然到期**（`MobEffectEvent.Expired`）才结算一次；提前移除 / 目标死亡 /
  实体离开世界 / 读档 **都不结算并清空提取值**；结算自身造成的伤害不回喂提取值（settling 标记）。
- ⚠ **字面公式的必然结果**：窗口内一次伤害都没挨到（提取值 0）时，结算仍是 `等级 × 每级固定伤害` 点
  （1 级 1 点、5 级 5 点），**不会**因为提取值为 0 就跳过结算（旧实现是 `存储 ≤ 0` 直接 return）。
  这一条已实机验证（第七节 CASE-A2 = 5.0），请作者知悉。

### 4.4 配置（`config/bettergold-common.toml`）

| 键 | 默认 | 含义 |
|---|---|---|
| `voodooExtractRatio` | `0.36` | 窗口内伤害的提取比例（36%） |
| `voodooFlatPerLevel` | `1.0` | 每级固定伤害（= 公式里加在 36% 后面的那一项，即「+ buff 等级」） |

- **取代**旧的 `voodooStoreRatio`（默认 0.8）与 `voodooReleasePerLevel`（默认 0.8）——两个旧键**已从 `Config` 删除**；
  作者/玩家手里的旧配置文件里残留这两个键会被 NeoForge 当作未知键忽略，新键按默认值生成。

## 五、仓库现状与实现方案

- **资产与数据 5 个生成器 + 2 个校验器**（`tools/asset-generator/`）：`generate_metal_assets.py` /
  `generate_metal_data.py` / `generate_metal_tags.py` / `generate_metal_recipes.py` / `generate_metal_trims.py`，
  校验用 `validate_metal_assets.py` / `validate_metal_data.py`。
- **标签体系现成**：家族标签 `bettergold:{ingots,nuggets,raw_materials,storage_blocks}`（物品 + 方块）
  + `c:` / `minecraft:` 桥接 + 挖掘等级 + 附魔类别标签，全由 `generate_metal_tags.py` 写入。
- **新机制需要的 Java 改动**（下一轮，1.4 的设施可直接复用）：
  1. 靛海金建材「对 4 种生物造成接触伤害」→ 扩展 `MetalEvents.applyContact` / `Spec` 增加一个「接触伤害」开关 + 目标类型集合；

  4. `AllEffects` 加 `SEDIMENT` / `SOOTHE`，`MetalSpecialItems` 加 `INDIGO_OCEAN_HEART` / `CHORUS_CHERRY_BRANCH`；
  5. 安抚的 AI 状态表（照 `VoodooAccumulator` 写）。
- **⚠ 前置条件**：1.4 的原料合成配方实现有 bug，**必须先修**，否则新金属原料做不出来 —— 见第九节。

  1 颗 = 2 点吸收值。
- ⚠ **吸收上限口径已被作者推翻（bg-15w 第 4 项，2026-10-02）**：
  旧口径（1.5 武器轮第一版）是盾牌的「**上限 4 点**」与盔甲的「4 点 × 件数」**取较大者（`max`）**；

  （`bettergold:absorption_cap`，值 = 相加后的合成值）。对照表与实测见 §13.6 / §14。
- 「武器耐久/附魔」在六套之间只有 6144/30 与 4096/24 两档（见 12.1），**没有第三档**。
- ⚠ **盾牌「不产生命中」这句已作废（bg-15w 第 3 项①）**：作者要求「用盾牌左键打怪也要给该金属的 buff」，
  `MetalEvents#dispatchWeaponHit` 现在放行**本族的盾牌**（走同一条统一派发链）；
  `MetalFamily#weapons()` 保持原样（盾牌仍不在那个列表里），
  所以靛海金双倍伤害一类「以 `weapons()` 为判据」的规则**不会**顺带作用于盾牌。
- **新增（bg-15w 第 3 项②，续工轮 §7.5 修正了落地方式）**：主手**或**副手拿着本模组盾牌 ⇒
  `KNOCKBACK_RESISTANCE +0.10`（10%），万坚金与特殊金属**都算**；
  主/副手共用**一个**修饰符 id（`bettergold:shield_knockback_resistance`），
  两只手各拿一个仍是 +10%；放下即移除。与盔甲的 `armorKnockbackResistance = 0.15F` **互不相干、不合并不改数**。
  - ⚠ **落地方式已改（续工轮 §7.5）**：上一轮是「`EntityTickEvent.Post` 里每 tick 挂一个 transient 修饰符」，
    本轮改成**物品自带**（`Item.Properties#attributes(...)`，MAINHAND + OFFHAND 两条、同一个 id）。
    三条实测依据见 **§16.2**：① 服务端**有效**（真实玩家 `knockback()` 位移 0.4000 → 0.3600，比值 0.9000，
    两手各拿仍只有一份）；② **物品 tooltip 里原本没有那一行**（改前 `lines=1`，只有物品名）——作者说的「**自带**」
    正是这一层，改后 tooltip 出现 `item.modifiers.mainhand` 与 `item.modifiers.offhand` 两行 `+10% 击退抗性`；
    ③ **客户端属性实例上永远看不到**，而且这是**原版行为、不是缺陷**：
    `Attributes.KNOCKBACK_RESISTANCE` 未 `setSyncable(true)`（`Attributes.java:86-89`），
    而装备属性只在服务端应用（`LivingEntity#tick()` 的 `detectEquipmentUpdates()` 整块在
    `if (!isClientSide)` 内，`LivingEntity.java:2457,2482`）——阳性对照：手里拿铁剑时客户端
    `attack_damage` 同样是 `{v=1.0,ids=[]}`。决定击退的是服务端，那里生效。

### 12.4 两条必须单独强调的规则

**(1) 无论近战还是远程，只要是一次攻击，都要能触发对应特殊金属武器的功能**

现状（1.5 已实现的部分）只有**近战**一条路：`MetalEvents#onLivingDamaged`
（`LivingDamageEvent.Post`）里 `source.getEntity() instanceof LivingEntity attacker` →
`attacker.getMainHandItem()` → `MetalFamily.of(stack)` → 按家族派发 buff/落雷。

**远程时这条链会断**（源码级原因）：

- 弓箭 / 弩箭命中时 `DamageSource#getEntity()` 是**射手**，但伤害来自 `AbstractArrow`；
  弩在装填完成后的那一发、以及射手换手、投掷物飞行期间换物品，都会让
  「命中瞬间的主手物品 ≠ 发射它的武器」→ 用主手判定会漏或错。
- **投掷三叉戟**命中时武器已经离手（`TridentItem#releaseUsing` 里
  `player.getInventory().removeItem(stack)`，`TridentItem.java:99-101`），主手是空的 → 必然漏判。

**统一派发的正确钥匙是 `DamageSource#getWeaponItem()`**
（neoforge sources `net/minecraft/world/damagesource/DamageSource.java:71-72`）：

```java
public ItemStack getWeaponItem() {
    return this.directEntity != null ? this.directEntity.getWeaponItem() : null;
}
```

- 近战：`directEntity` = 攻击者本体 → `LivingEntity#getWeaponItem()` = **主手物品**（与现状等价）；
- 弓箭 / 弩箭：`directEntity` = `AbstractArrow`，其 `getWeaponItem()` 返回 **`firedFromWeapon`**
  （`AbstractArrow.java:499-501`），也就是那把**弓 / 弩**；
- 三叉戟：`ThrownTrident` 的 `getWeaponItem()` 返回**那把三叉戟本身**。

⇒ 下一轮（1.5 武器轮）的实现方案（照做）：

1. 把现有 `onLivingDamaged` 里的判定从 `attacker.getMainHandItem()` 抽成一个
   `dispatchWeaponHit(LivingEntity attackerOrOwner, ItemStack weapon, LivingEntity target)`；
2. 事件里用 `ItemStack weapon = event.getSource().getWeaponItem()` 取武器
   （为空时回落到 `source.getEntity()` 的主手，保证 1.4/1.5 的既有行为一个字节不变）；
3. 远程与近战**共用这一个** `dispatchWeaponHit`（`LivingDamageEvent.Post` 对箭/三叉戟的命中同样会发），
   于是「近战还是远程」对特殊功能的派发不再有区别；
4. **回归要求**：改完后必须重跑 1.5 修正轮的 A2/A4 与 11.4 的 ⑪ 器具攻击附加，
   数字要与 1.5 实测逐字一致（改派发链最容易把既有行为弄漂）。

> ✅ **1–3 已在 1.5 武器轮第一版落地**（`MetalEvents#onLivingDamaged` / `#weaponOf` / `#dispatchWeaponHit`），
> 本轮（bg-15w）只在这条链上补一条：**盾牌也算「武器」**（第 3 项①，见 §12.3 的说明）。

**(1b) 掷出去的三叉戟（bg-15w 第 1 项 (b)：这一点原规格没写到，补档）**

- 症状：**扔出去飞行 / 落在地上的样子是原版三叉戟**。
- 根因（两条叠加）：① 物品侧与实体侧是**两套**渲染 —— 物品走
  `BlockEntityWithoutLevelRenderer`（本模组已有 `MetalWeaponItemRenderer`），
  实体走 `EntityRenderer`，而原版 `ThrownTridentRenderer#getTextureLocation` 把贴图**写死**成
  `minecraft:textures/entity/trident.png`；
  ② 更麻烦的是**金属信息在客户端根本不存在**：原版 `AbstractArrow` 把物品栈放在普通字段
  `pickupItemStack` 里（`AbstractArrow.java:71`），`defineSynchedData` 只同步
  `ID_FLAGS` / `PIERCE_LEVEL`（同文件 138-141 行）⇒ 客户端那个实体恒为
  `getDefaultPickupItem()` = **原版三叉戟**，渲染器从物品栈反查金属永远查不到。
- 落档修法：注册自己的实体渲染器（`EntityRenderersEvent.RegisterRenderers` 整体替换
  `EntityType.TRIDENT`）+ **在投掷时写入金属 id 并用同步附件送过去**
  （`registry/AllAttachments#THROWN_TRIDENT_METAL`，`MetalEvents#onEntityJoinLevel` 在服务端实体进世界时写）。
  贴图 id 的拼法**与物品侧共用同一个方法**（`MetalWeaponItemRenderer#tridentTexture(String)`）。
  非本模组的三叉戟回落原版贴图 ⇒ 对原版 / 其它模组无副作用。

**(1c) 「模型全黑」的真根因（bg-15w 第 1 项 (a)：原规格把它列为待修，根因与规格推测的不同）**

- 规格 12.7 未列此条；需求 §3.1(a) 的嫌疑排序是「① 登记时机太晚 ② 贴图 id 拼错 ③ PNG 全黑」。
- **实测结论 = ②**：登记时机**没问题**（日志逐字为「已为 6 件盾牌 + 6 件三叉戟登记自定义物品渲染器」，
  12 件齐全），12 张 PNG 也**都不是全黑 / 全透明**（盾 716/4096 不透明像素、三叉戟 209/1024，max alpha 255）。
  真正的错在 `MetalWeaponItemRenderer` 拼的贴图 id **少了 `textures/` 前缀与 `.png` 后缀**：
  `RenderType.entitySolid(ResourceLocation)` 走 `SimpleTexture`，而
  `SimpleTexture.TextureImage.load` 是 `resourceManager.getResourceOrThrow(location)`——
  **原样当资源路径用、不做任何补全**（`SimpleTexture.java:81-83`；原版常量形如
  `TridentModel.TEXTURE = "textures/entity/trident.png"`）。
  写错时每次都抛 `FileNotFoundException: bettergold:entity/shield_<金属>`，
  `TextureManager#loadTexture` 吞掉异常返回 missingno（16×16 四象限，左上为纯黑），
  而盾 / 三叉戟模型的 UV 恰好整块落在那个黑色象限 ⇒ **整个模型渲染成纯黑**。
- 全套证据（件数 / 贴图 id 逐字比对 / 像素统计 / 日志栈）见 **§14**。

**(1d) bg-15x：古董器具「掉落尘埃」也改用同一把钥匙（作者裁定「是」）**

- 位置：`ModEvents#onLivingIncomingDamage`（`event/ModEvents.java:191-212`）。
  bg-15w 只把「万坚金掉落金」那条分支换成 `MetalEvents.weaponOf(...)`
  （= `DamageSource#getWeaponItem()`，为空回落主手），**「古董器具 → 下界合金尘埃」那条仍按主手判定**
  ⇒ 投掷 / 远程命中时主手已空（或已换成别的东西）就会**静默漏判**（不报错、只是不掉尘埃）。
- 本轮把它一起换成 `weapon`：`isDustOnAttackTool(weapon)` + `enchantLevel(weapon, …)`；
  **只改取武器方式**，掉落物 / 概率 / 抢夺公式 / 数量 / 万坚金那条分支逐字未动；
  只被这两处引用的局部变量 `ItemStack held = player.getMainHandItem();` 随之下线。
- A 级实测见 **§15.1**：改前 8 件 PASS / 3 件 FAIL（三条投掷·远程用例全红、dust = 0），
  改后 **11 件 PASS / 0 件 FAIL**（古董投掷 18、古董箭 15、主手换木棍 17、近战 15；
  万坚金两例仍 210 / 212 件掉落、特殊金属 0、无武器 0、古董镐 0）。

**(2) 盾牌「破盾」在原版 1.21.1 里到底是什么**

源码链（三段，缺一不可）：

1. `Player#blockUsingShield(LivingEntity entity)`（neoforge sources
   `net/minecraft/world/entity/player/Player.java:958-961`）：
   `super.blockUsingShield(entity); if (entity.canDisableShield()) this.disableShield();`
2. `LivingEntity#canDisableShield()`（同目录 `LivingEntity.java:3727-3728`，**NeoForge 改写过的**）：
   `return this.getMainHandItem().canDisableShield(this.useItem, this, this);`
   → `IItemStackExtension#canDisableShield(ItemStack shield, LivingEntity entity, LivingEntity attacker)`
   → `IItemExtension#canDisableShield(...)`，默认实现是
   **`return this instanceof AxeItem;`**（neoforge sources
   `net/neoforged/neoforge/common/extensions/IItemExtension.java:608-610`）。
   ⇒ **原版「破盾」= 攻击者主手是斧**（不是重锤、不是别的）。
3. `Player#disableShield()`（`Player.java:1428-1432`）：
   `this.getCooldowns().addCooldown(this.getUseItem().getItem(), 100); this.stopUsingItem();
   this.level().broadcastEntityEvent(this, (byte)30);`
   ⇒ 破盾的**实际效果**就是「给盾牌上 100 tick 冷却 + 停止格挡 + 播一个动画事件」。

**关键结论：判定点在攻击者的物品上，盾牌自己没有否决点，也没有对应的事件。**
所以「免疫破盾」需要我们自己动手，可行方案按推荐度：

| 方案 | 做法 | 代价 |
|---|---|---|
| **A（推荐，纯事件、无 mixin）** | `PlayerTickEvent.Post` 里，若玩家**主手或副手**拿着本模组的盾牌且
`player.getCooldowns().isOnCooldown(<该盾牌物品>)` → `getCooldowns().removeCooldown(item)`
（`ItemCooldowns#removeCooldown(Item)`）。冷却被抹掉 = 下一 tick 就能重新举盾，观感上「没被破盾」。 | 动画包 30（盾牌抖动）仍会播一次；需要每 tick（或每 5 tick）查一次 |
| B | 用 Mixin / 自定义 `Player` 覆写 `blockUsingShield` | 本仓库**没有 mixin 配置**（`build.gradle` 里没有 mixin 段），引入成本大 |

⇒ 结论：**需要自定义**，但用方案 A 就够，不需要 mixin。

> ⚠ **免疫范围的口径已被作者推翻（bg-15w 续工轮，2026-10-02）**：
> 上面这条链与「方案 A」的**做法**不变，但**判据**从「只给五套特殊金属」改成
> 「**本模组六种金属的盾牌全部免疫**」（作者原话「哦对了万坚金盾牌没有免疫破盾」）。
> 落点：`MetalEvents#onPlayerTickShieldImmunity` 判 `MetalShieldItem#isBreakImmune()`
> （`Spec#shieldBreakImmune`，默认 true），不再是 `isSpecialMetal()`。
> ⚠ 改前 `MetalFamily#shieldBreakImmune` 这个字段**只被赋值、从未被读**（真正判豁免的是
> `isSpecialMetal()`）——本轮把它接成了真正的判据，A 级实测见 §16.3（改前万坚金红、改后六种全绿）。
> 另外：`Player#blockUsingShield` 是 `protected`，探针无法直接调，所以 A 级用例走的是
> **同一条原版链的落点**——`attacker.canDisableShield()`（攻击者主手斧）+ `player.disableShield()`，
> 再隔 10 tick 读 `ItemCooldowns#isOnCooldown`（原版破盾 = 上 100 tick 冷却）。

**格挡反给攻击者 buff** 的落点是 NeoForge 现成事件：
`LivingShieldBlockEvent`（`net/neoforged/neoforge/event/entity/living/LivingShieldBlockEvent.java`，
在 `LivingEntity.java:1162-1167` 由 `CommonHooks.onDamageBlock(...)` 发出）：
`getBlocked()` 为真时，取 `getEntity()`（举盾者）的主/副手盾牌 → 家族 → 对
`getDamageSource().getEntity()`（攻击者）走与器具**同一个** buff 施加函数。

### 13.5 修正⑤ 靛海金盔甲单件 25% 游泳速度

- **属性选择（源码依据）**：用 `Attributes.WATER_MOVEMENT_EFFICIENCY`
  （`minecraft:generic.water_movement_efficiency`，`RangedAttribute(0.0, 0.0, 1.0)`，
  neoforge sources `net/minecraft/world/entity/ai/attributes/Attributes.java:145-147`），
  因为 `LivingEntity#travel` 在水里只读它（同目录 `LivingEntity.java:2231-2241`）：
  `f4 += (0.54600006F - f4) * f6`（把水中减速系数推向 0.546）+
  `f5 += (this.getSpeed() - f5) * f6`（把水中加速度推向陆地速度）
  —— **只影响游泳/水中移动**；`MOVEMENT_SPEED` 是陆地基础速度，用了会连走路一起变快，不是作者要的。
- **修法**：`MetalArmorItem#getDefaultAttributeModifiers()` 在盔甲原有属性表上
  `withModifierAdded(WATER_MOVEMENT_EFFICIENCY, +0.25, 该部位)`（不改 `Item.Properties`，
  否则会把护甲/韧性一起丢掉）。
  ⚠ **探针抓到过一个真 bug**：四个部位最初共用同一个修饰符 id `bettergold:swim_speed`，
  属性修饰符按 id 去重 → **穿 4 件也只有 0.25**；改成每部位一个 id
  （`swim_speed_helmet/chestplate/leggings/boots`，与原版 `ArmorItem` 的 `armor.<type>` 同构）后正常。
- **实测**：

| 件数 | `waterMovementEfficiency` |
|---|---|
| 0 件（基线） | 0.0000 |
| 1 件 | **0.2500** |
| 4 件 | **1.0000** |

- **四件叠到 100% 时的表现（要说明的）**：`f6 = 1.0` 时水上公式退化为
  `f4 = 0.54600006`（水中阻力系数从 0.8/0.9 降到底）、`f5 = getSpeed()`（加速度 = 陆地速度）
  ⇒ **在水里以陆地速度游**（原版「深海漫游」级别的顺滑）。两点边界：
  ① 该属性被 `RangedAttribute` 夹在 `[0, 1]`，**四件就是封顶**，再多也不会超过 1.0；
  ② `!onGround()` 时原版会 `f6 *= 0.5F`（`LivingEntity.java:2234-2236`），
  所以**离地（悬在水中）时实际只有一半效果**，贴地游泳才是满效果。
- **⚠ 本条不是"水中游泳速度"的全部**（bg-15w §八 8.3 追加，2026-10-02 17:44）：作者澄清
  「这次更新所提供的水中移速率指的是提供于**一格高的水面上移动加快**，而不是**游泳加快**」，
  因此**新加了一条**真正的水中游泳速度（`MOVEMENT_SPEED` + `ADD_MULTIPLIED_TOTAL` 的条件修饰符，
  一个 id `bettergold:swim_speed_water`，值 = 0.25 × 件数）。
  **上面这一个常量与四个部位 id 一个字都没动**；两条并存、不合并。
  新那条的落点、真玩家实测数字，以及"端到端位移比值 **不是** 1.25×/件"的机理见 **§17.3 / §17.4**。

### 13.7 修正⑦ 盔甲纹饰显示成白色（根因 + 修法 + 两段实测）

3. **我们七个纹饰材质的 `item_model_index` 全撞在原版值上**（改动前：六个金属 **0.1 = quartz**、
   unwanted_antique 0.2 = iron）⇒ 任何一件原版盔甲打上我方纹饰，命中的都是

### 16.2 §7.5 的三份取证（先取证 → 再决定改哪里）

> **背景**：上一轮那 4 条击退抗性断言是 **`FakePlayer` + 探针手工 post `EntityTickEvent.Post`** 测出来的
> （它自己的留档里就写着 `fake_player_created` / `probe counted 8 ticks`）⇒ 只能证明"那段 handler 算术对"，
> **不能证明真实玩家会被 tick 到那一段**。所以本轮换成**真实玩家**重测。

**① 读实现（改前）**：`MetalEvents#onShieldKnockbackTick`（`EntityTickEvent.Post`）——
服务端、`heldShield(...)` 命中即 `addOrUpdateTransientModifier`、否则 `removeModifier`；
一个 id（`bettergold:shield_knockback_resistance`）、`ADD_VALUE 0.10`。静态看不出问题。

**② 真玩家实测（改前基线 = `docs/bg7-证据/01-改前基线-run1b-探针结果.txt`）**

| 观察面 | 实测 | 判定 |
|---|---|---|
| 服务端属性值 | 主手 `0.1000` / 副手 `0.1000` / 两手各一个仍 `0.1000`（实例上**只有 1 条**修饰符）/ 放下 `0.0000` | ✅ 生效 |
| **玩法效果** | `knockback()` 真实位移：无盾 `|dx|=0.4000`、有盾 `|dx|=0.3600` ⇒ **比值 0.9000** | ✅ 生效 |
| 真实玩家是否被 tick 到 | 探针自己订阅 `EntityTickEvent.Post` / `PlayerTickEvent.Post` 计数均 > 50，逐 tick 采样里能看到 `ids=[bettergold:shield_knockback_resistance]` | ✅ 不是"没跑到" |
| **物品 tooltip** | 六种盾牌 `lines=1`（**只有物品名**，没有任何属性行） | ❌ 看不见 |
| **客户端属性实例** | 三种持盾情形恒为 `0.0000 / ids=[]` | ❌ 拿不到（见下） |

**③ 「客户端看不到」的根因（源码级，且**不是**本模组造成的）**

- `Attributes.KNOCKBACK_RESISTANCE` 在 NeoForge 里注册时**没有** `.setSyncable(true)`
  （neoforge sources `Attributes.java:86-89`；`Attribute.syncable` 字段默认 `false`，
  见 `Attribute.java:26,42-43`）⇒ 它永远不进 `ClientboundUpdateAttributesPacket`；
- 而**装备**带来的属性修饰符本身也只在服务端应用：`LivingEntity#tick()` 里
  `this.detectEquipmentUpdates()` 整块位于 `if (!this.level().isClientSide) { ... }` 之内
  （`LivingEntity.java:2457,2482`）；
- **阳性对照（本轮实测）**：手里拿**铁剑**时，服务端 `attack_damage={v=6.0000,ids=[minecraft:base_attack_damage]}`，
  客户端 `attack_damage={v=1.0000,ids=[]}` —— **原版物品在客户端也没有物品属性修饰符**。
  ⇒ 客户端看不到是**原版行为**，与本次改动无关；决定击退的是服务端，那里生效。

**⇒ 结论与改法**：机制一直有效，但作者说的「**自带**主副手持的 10%」这一层（物品自带 / tooltip 可见）
**确实没有**。所以把口径落成**物品自带**（一个 id、MAINHAND + OFFHAND 两条），
改后实测：服务端四条全绿（0.10 / 0.10 / 0.10 / 0.00）＋ 位移比值仍 **0.9000** ＋
**六种盾牌 tooltip 各 7 行、其中 `item.modifiers.mainhand` 与 `item.modifiers.offhand` 两行都是 `+10% 击退抗性`**。
与盔甲侧 `armorKnockbackResistance = 0.15F` 仍然**互不相干、不合并不改数**。

> ⚠ **一处旧结论的更正（供经验库）**：上一轮写下的「物品属性表给两个槽位组各一条会抛
> `IllegalArgumentException` 或叠加成 +20%」**前提不完整**：`LivingEntity#handleEquipmentChanges`
> 应用物品属性时是**先 `removeModifier(modifier.id())` 再 `addTransientModifier(modifier)`**
> （`LivingEntity.java:2628-2633`），同 id 是覆盖而不是重复添加；而
> `ItemAttributeModifiers.Builder` 用的是 `ImmutableList.Builder`（`ItemAttributeModifiers.java:102-113`），
> 允许同一 (属性, id) 挂两个槽位组。**本轮实测两手各拿仍只有 +10%**。

### 17.4 ⚠ 与需求括号里那句期望不符的地方（**这一条必须让作者知情，等裁定**）

需求 §8.3 的验收口径写的是「水里与陆地各测 0/1/2/3/4 件的实际移动速度比值（**水中应为 1.25×/1.5×/1.75×/2.0×**）」。
本轮实测结果分成**两句话**，必须分开说：

| 口径 | 实测 | 与需求的期望 |
|---|---|---|
| **`MOVEMENT_SPEED` 属性值**的比值 | **1.2500 / 1.5000 / 1.7500 / 2.0000**（服务端与客户端逐值相同） | ✅ **精确命中** |
| **端到端位移**的比值 | **1.7574 / 2.6031 / 3.4941 / 4.4116** | ❌ **不等于** 1.25/1.5/1.75/2.0 |

**根因（源码级，不是测量误差）**：

1. `LivingEntity#travel` 的水中分支里，`MOVEMENT_SPEED` **不是最终乘数**，它只以
   `f5 += (this.getSpeed() - f5) * f6` 的形式参与（neoforge sources `LivingEntity.java:2238-2241`）——
   `f5` 的初值是 **0.02**，**抬高 `getSpeed()` 只是抬高混合目标**；而 `f6` 正是我们**保留的**
   `WATER_MOVEMENT_EFFICIENCY`，并且 `!onGround()` 时原版还会 `f6 *= 0.5F`（§13.5 已记载）。
2. 同一条里 `f4 += (0.54600006F - f4) * f6` 又把**水中阻力系数**一起改了 ⇒
   "保留的那条"自身就已经让水中位移涨到 **1.52 → 2.21**（上表改前列），两条叠起来必然是**超线性**的。

⇒ **若作者要的是「水中位移严格 ×1.25/件」**，那一层应该落在 **`neoforge:swim_speed`**
