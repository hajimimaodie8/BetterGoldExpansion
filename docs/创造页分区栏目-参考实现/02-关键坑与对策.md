## §1 `output.accept(ItemStack.EMPTY)` **会抛异常**，不是被过滤

**现象**
在 `displayItems` 生成器里用 `output.accept(ItemStack.EMPTY)` 想插一个空行，结果整个标签页的物品构建**中断**，
异常信息是 `IllegalArgumentException: The stack count must be 1`（有些路径下是 `Stack size must be exactly 1`）。
不是「空 Stack 被悄悄忽略」，而是**直接抛**。

**根因**
有两道一模一样的校验，都在检查 `count == 1`：

1. NeoForge 的包装层最先命中。【读源码】`EventHooks.onCreativeModeTabBuildContents`
   （`neoforge-21.1.228-sources.jar` → `net/neoforged/neoforge/event/EventHooks.java:1104-1119`）：

   ```java
   originalGenerator.accept(params, (stack, vis) -> {
       if (stack.getCount() != 1)
           throw new IllegalArgumentException("The stack count must be 1");   // 第 1109-1110 行
       ...
   });
   ```

   你在生成器里拿到的 `Output` 就是上面这个 lambda 包装出来的，所以它先炸。
2. 原版自己也有。【读源码】`CreativeModeTab.ItemDisplayBuilder#accept`
   （`CreativeModeTab.java:392-394`）：

   ```java
   public void accept(ItemStack stack, CreativeModeTab.TabVisibility tabVisibility) {
       if (stack.getCount() != 1) {
           throw new IllegalArgumentException("Stack size must be exactly 1");
       }
   ```

而 `ItemStack.EMPTY.getCount()` 是 **0**（EMPTY 的定义就是一个 count 为 0 的空栈），所以必然命中。

**修法（我们采用的）**
**不要在 `Output` 里塞空行。** 让生成器只 accept 非空格子，空行改在 `CreativeModeTab#getDisplayItems()` 里补：

```java
// SectionedCreativeTab.Layout#build（生成器）
for (ItemStack stack : laidOut) {
    if (!stack.isEmpty()) output.accept(stack);     // 空格子一个都不 accept
}
```

这么做之所以成立，是因为**创造界面本来就是从 `getDisplayItems()` 取内容的**，而且原版自己也往这个列表里放 `EMPTY`：

- 【读源码】`CreativeModeInventoryScreen#selectTab` 第 643 行：
  `this.menu.items.addAll(selectedTab.getDisplayItems());`
  （同类页 `Type.CATEGORY` 走这一支；快捷栏页在 selectTab 里是第 620-641 行）
- 【读源码】同方法第 635 行：`this.menu.items.add(ItemStack.EMPTY);`
  —— 原版**自己**往 `menu.items` 里塞空格子（快捷栏页的空位），所以「列表里有空格子」是原版支持的形态。
- 【读源码】`refreshSearchResults` 第 505 行：`this.menu.items.addAll(selectedTab.getDisplayItems());`

**对比：参考实现为什么能塞空行**
【读源码】Aeronautics 用 `@Mixin(CreativeModeTab.class)` + `@Shadow private Collection<ItemStack> displayItems`
直接**替换私有字段**（`CreativeModeTabMixin#simulated$buildContents`），完全不经过 `Output` 校验，
所以它的 `addEmptySlots` 写 `items.add(ItemStack.EMPTY)` 是合法的。我们不走 Mixin，就没有这个特权。

**顺带一条**：即使你不塞空行，也要注意 `accept` 会对**重复 stack** 抛
`IllegalStateException("Accidentally adding the same item stack twice ...")`（`CreativeModeTab.java:396-403`）。
所以分桶时每件物品只能进一个桶（`01` §2 的 `taken[]`），这既是排序需要，也是这个校验的要求。

## §2 GUI 图集只扫 `textures/gui/sprites/`：`blitSprite` 查不到会**静默**退化成紫黑格

**现象**
横幅贴图放在 `assets/<ns>/textures/gui/creative_sections/xxx.png`，用 `graphics.blitSprite(...)` 绘制，
结果**什么都没画出来**（该位置是紫黑相间的 missing texture 图案），而且
**客户端日志里一条报错、一条警告都没有**。这是本条最恶劣的地方：它把「路径写错」伪装成「没执行到」。

**根因（三层，全部【读源码】）**

1. `GuiGraphics#blitSprite` 只查 GUI 图集：
   `GuiGraphics.java:681-683` → `TextureAtlasSprite s = this.sprites.getSprite(sprite);`，
   而 `this.sprites` 在构造器 `GuiGraphics.java:74` 被赋成 `minecraft.getGuiSprites()`。
2. 这个图集的定义只有一个目录源：
   `GuiSpriteManager` 构造器 `GuiSpriteManager.java:20` 把 atlas info 定为 `minecraft:gui`，
   即读取 `assets/minecraft/atlases/gui.json`。**把客户端 jar 里这个文件抓出来看**（命令见 `05` §4）：

   ```json
   {
       "sources": [
           { "type": "directory", "source": "gui/sprites", "prefix": "" }
       ]
   }
   ```

   即：GUI 图集**只**收录 `assets/<ns>/textures/gui/sprites/**` 下的图（1.21.1 原版这个目录下有 422 个文件）。
   `textures/gui/` 的其它子目录（含我们的 `gui/creative_sections/`）**不在任何图集里**。
3. 查不到不报错：`TextureAtlas#getSprite`（`TextureAtlas.java:141-142`）

   ```java
   public TextureAtlasSprite getSprite(ResourceLocation name) {
       return this.texturesByName.getOrDefault(name, this.missingSprite);
   }
   ```

   —— `getOrDefault` 落到 `this.missingSprite`，也就是那个紫黑格子。**不抛异常、不打日志**。

**修法（三选一）**

| 选项 | 做法 | 代价 |
|---|---|---|
| **A. 用 `blit`（我们的选择）** | `graphics.blit(贴图RL, x, y, 0, 0F, 0F, w, h, texW, texH)`，直接 blit 整张贴图，不经过图集 | 不能用图集特性（动画帧、九宫格缩放、hover 换帧）；贴图尺寸要与绘制尺寸一致 |
| **B. 放进 `gui/sprites/`** | 资源放 `assets/<ns>/textures/gui/sprites/<名字>.png`，代码写 `blitSprite(ResourceLocation.fromNamespaceAndPath(ns, "<名字>"), x, y, w, h)` | 路径规则更绕（`textures/` 与 `.png` 都要去掉，还要去掉 `gui/sprites/` 前缀）；想要动画还得配 `.mcmeta` |
| **C. 自建 atlas 定义扩展 gui 图集** | 写 `assets/<ns>/atlases/gui.json`，加一条 `directory` source 指向你的目录 | 需要额外资源文件。【读源码】可行依据：`SpriteSourceList#load`（`SpriteSourceList.java:70-84`）用的是 `resourceManager.getResourceStack(resourceloc)`（第 74 行），会**堆叠合并所有资源包的同名 atlas 定义**。**本机未实测 C**，标【读源码/未实测】 |

A 的先例（【读源码】）：原版创造界面自己的背景就是 `graphics.blit(...)`：
`CreativeModeInventoryScreen.java:847`
`guiGraphics.blit(selectedTab.getBackgroundTexture(), this.leftPos, this.topPos, 0, 0, this.imageWidth, this.imageHeight);`

**互证（【读源码】+ 仓库文件清单）**
参考实现 Aeronautics 仓库里**同时存在两套横幅图**：

- `simulated/common/src/main/resources/assets/simulated/textures/gui/banner/{aeronautics,high_seas,offroad,simulated_}.png`
  —— 一个**不在图集里**的目录；
- `simulated/common/src/main/resources/assets/{simulated,aeronautics,offroad}/textures/gui/sprites/banner.png` + `banner.png.mcmeta`
  —— **在图集里**的那一份。

而它的分区 JSON（`assets/simulated/simulated/sections/simulated.json`）写的是 `"sprite": "simulated:banner"`，
`Simulated:banner` 对应 `textures/gui/sprites/banner.png`；它的 `setPlaying` 也是走
`Minecraft.getInstance().getGuiSprites().getSprite(...)`（`SimulatedCreativeTab.java:214`）。
也就是说：**真正被 `blitSprite` 画出来的是 `gui/sprites/` 里那一份**。

**为什么日志取不到证**
因为坏路径**不报错**，所以「本机曾看到紫黑格」这件事在日志里留不下痕迹 —— 这条只能靠读源码确认机制。
原作者把现象记在 `docs\构建与跑测注意事项.md:51-53`（【记录】）。

## §3 `DeferredHolder` 别名**不能**写成 `= Family.holder`：类初始化循环（NPE）

**现象**
编译完全通过，`runServer` 在 mod 构造阶段（首次触碰注册表时）崩：

```
Exception in thread "main" java.lang.ExceptionInInitializerError
    at Family.<init>(CycleDemo.java:43)
    at AllMetals.<clinit>(CycleDemo.java:29)
    at AllBlocks.<clinit>(CycleDemo.java:24)
    at CycleDemo.main(CycleDemo.java:7)
Caused by: java.lang.NullPointerException: Cannot read field "ingot" because "AllMetals.STURDYGOLD" is null
    at AllItems.<clinit>(CycleDemo.java:18)
```

**根因**
JVM **不会重入**一个正在初始化中的类。链条是：

```
AllBlocks.<clinit>
  → 读别名 AllMetals.STURDYGOLD.ingot
    → 触发 AllMetals.<clinit>
      → 家族构造器注册物品/方块（要往 AllItems.ITEMS / AllBlocks.BLOCKS 里塞）
        → 触发 AllItems.<clinit>
          → AllItems 的字段初始化又要读 AllMetals.STURDYGOLD
            → 它还在初始化中 ⇒ JVM 直接返回「尚未赋值」⇒ null
              → NullPointerException
```

**证据（最小复现，【实测】）**
`build\scratch\CycleDemo.java`（约 50 行的自包含复现，用 `java CycleDemo.java` 直接跑，不依赖 Gradle）
产生的完整栈在 `build\scratch\cycle-demo.log`（上文引用的就是它的内容）。
前序开发在 `docs\1.4-进度与交接.md:25` 也记录了同一结论。

**修法：改用「不参与注册的懒绑定别名」**

```java
/** 按注册名建一个物品别名（不注册，只懒绑定） */
public static <T extends Item> DeferredItem<T> item(String path) {
    return DeferredItem.createItem(ResourceLocation.fromNamespaceAndPath(MODID, path));
}
/** 按注册名建一个方块别名（不注册，只懒绑定） */
public static <T extends Block> DeferredBlock<T> block(String path) {
    return DeferredBlock.createBlock(ResourceLocation.fromNamespaceAndPath(MODID, path));
}
```

**为什么这样就没有循环（【读源码】，三处）**

- `DeferredItem.createItem(ResourceLocation)`：`DeferredItem.java:46-48` → `new DeferredItem<>(ResourceKey.create(Registries.ITEM, key))`，
  **只构造对象，不查注册表、不触发注册**。
- `DeferredBlock.createBlock(ResourceLocation)`：`DeferredBlock.java:47-48`，同理。
- `DeferredHolder(ResourceKey)`（`DeferredHolder.java:87`）造出来是**未绑定**的；第一次 `get()`/`value()`
  时才 `bind(true)`，用 `registry.getHolder(this.key)` **现查**（`DeferredHolder.java:148-157`）。
  因此它解析到的就是家族注册的**同一个**注册项 —— 不会造成第二次注册，也永远不会在类初始化阶段去读注册项。

**这一条的通用纪律（比这个坑本身更值钱）**
> **类初始化期间只能「构造对象」，不能「读取注册项」。**

**姊妹坑：注册期不能 `.get()`**
【读源码】`DeferredHolder.value()` 第 100-107 行：

```java
public T value() {
    bind(true);
    if (this.holder == null) {
        throw new NullPointerException("Trying to access unbound value: " + this.key);   // 第 103 行
    }
```

所以在 `RegisterEvent` / `FMLCommonSetupEvent` 之前调用 `.get()` 会抛
`Trying to access unbound value: <key>`。任何「注册名 → 物品」的反查表（例如「某金属的核心材料物品」）
都必须做成**懒解析 + 缓存**，不能在建表时就 `get()`。

## §4 横幅行必须**整行皆空**才画；渲染端不要写死 `−1`

**现象**
横幅（半透明贴图）压在物品图标上，或释词文字挡住物品；也可能整条横幅不画（行号越界/负数）。

**根因**
如果渲染端硬编码「横幅行 = `SECTION_ROWS` 记录值 − 1」，那么这个**等式只在「列表内容与生成时完全一致」
且「记录的就是首物品行」**的前提下成立。以下任一情况都会让它失准：

- 别的模组通过 `BuildCreativeModeTabContentsEvent` 往本页插了/删了物品（长度守卫会因此触发回退，见 `01` §8）；
- 你自己后来改了约定（例如像参考实现那样改记「横幅行」，见 `01` §5.4）；
- 分区物品数为 0（空桶）等边界情况。

**修法：自适应判定 —— 只认「整行空格子」这个事实**

```java
/** anchor = SECTION_ROWS 记录值 − 首个可见行 */
private static int bannerRow(ItemPickerMenu menu, int anchor) {
    if (isRowEmpty(menu, anchor))     return anchor;        // 记录值本身就是空行（记的是横幅行）
    if (isRowEmpty(menu, anchor - 1)) return anchor - 1;    // 记录值是首物品行 → 上一行是横幅行
    return -1;                                              // 两行都不空 ⇒ 不画
}

private static boolean isRowEmpty(ItemPickerMenu menu, int row) {
    if (row < 0 || row >= VISIBLE_ROWS) return false;       // 可见行只有 0..4
    int first = row * ITEMS_PER_ROW;
    if (first + ITEMS_PER_ROW > menu.slots.size()) return false;
    for (int i = first; i < first + ITEMS_PER_ROW; i++) {
        if (menu.getSlot(i).hasItem()) return false;         // 有一个非空就不算空行
    }
    return true;
}
```

这段代码（`client\CreativeSectionBanners.java` 的 `bannerRow` / `isRowEmpty`，现位于 `:171-197`）同时兜住两种记录语义，并且
**从构造上保证绝不会把横幅画到物品上**。代价是每帧多做 9~18 次 `hasItem()`，可忽略。

**依据**

- 【读源码】「可见行 → 物品索引」的权威映射在 `ItemPickerMenu#scrollTo`
  （`CreativeModeInventoryScreen.java:1048-1061`）：`int l = k + (j + i) * 9;`，
  `i` = 首个可见行、`j` = 可见行、`k` = 列；越界或为空则 `setItem(..., ItemStack.EMPTY)`。
  所以「某个可见行的 9 个槽位都空」是可以用 `menu.getSlot(0..44)` 直接判定的。
- 【实测】逐行空判定真的跑过：`build\banner-runClient2.log:875-879`

  ```
  [TEMP-BANNER]   visibleRow 0 empty=false
  [TEMP-BANNER]   visibleRow 1 empty=true
  [TEMP-BANNER]   visibleRow 2 empty=false
  [TEMP-BANNER]   visibleRow 3 empty=false
  [TEMP-BANNER]   visibleRow 4 empty=false
  ```

  与同一帧的分区行判定（`:859-874`，`anchorRow=2 -> row=1 screenY=87`）自洽：横幅画在第 1 可见行，而第 1 行确实是空行。
- 【读源码】**反例说明为什么参考实现可以省掉这层防御**：Aeronautics 的 `renderBanners` 直接
  `int sectionRow = yValue - CURRENT_ROW;` 然后 `if (sectionRow < 0 || sectionRow > 4) continue;`，
  **不检查那一行是否真的全空** —— 因为它用 Mixin 完全独占了该标签页的物品构建，列表内容不会被别人改。
  我们用公开 API 与其它模组共存，所以必须防御。

**顺带一个措辞坑**：不要把「整行空」判成「`items` 列表里对应位置是 EMPTY」。渲染时应该读**槽位**
（`menu.getSlot(i).hasItem()`），因为槽位才是真正被绘制的东西，而槽位内容由原版 `scrollTo` 从 `items` 拷来，
两者本应等价 —— 读槽位可以在「拷贝逻辑被别的模组改了」时自动跟随。

## §5 创造页排序：`withTabsBefore` 的语义 + **不要**锚 `DEFAULT_TABS`

**现象**
自己的页跑到创造界面的**第二页**（原版页被挤走），或者顺序莫名其妙、和自己的预期相反。

**语义（【读源码】+ 原版 javadoc）**
`CreativeModeTab.java:320-327`：

```java
/** Define tabs that should come <i>before</i> this tab. This tab will be placed <strong>after</strong> the {@code tabs}. **/
public CreativeModeTab.Builder withTabsBefore(ResourceLocation... tabs)   // 第 321 行
/** Define tabs that should come <i>after</i> this tab. This tab will be placed <strong>before</strong> the {@code tabs}.**/
public CreativeModeTab.Builder withTabsAfter(ResourceLocation... tabs)    // 第 327 行
```

记法：**`withTabsBefore(X)` = 「X 在本页之前」**（本页排在 X 后面）。
`withTabsAfter(X)` = 「X 在本页之后」（本页排在 X 前面）。两者读起来都容易反，写完务必看一眼注释。

**根因（【读源码】，NeoForge 21.1.228）**
`CreativeModeTabRegistry` 的排序过程：

```java
// recalculateItemCreativeModeTabs()，第 137-155 行
for (CreativeModeTab tab : BuiltInRegistries.CREATIVE_MODE_TAB) {
    if (!DEFAULT_TABS.contains(tab))
        graph.addNode(tab);                    // 第 140-143 行：只有「非默认页」成为节点
}
edges.forEach((key, value) -> {
    ...
    graph.putEdge(keyC, valueC);               // 第 144-149 行：边是无条件下进去的
});

// sortTabs()，第 173-215 行
DEFAULT_TABS.add(... HOTBAR ...);              // 第 176 行
DEFAULT_TABS.add(... SEARCH ...);              // 第 177 行
DEFAULT_TABS.add(... OP_BLOCKS ...);           // 第 178 行
DEFAULT_TABS.add(... INVENTORY ...);           // 第 179 行
```

`DEFAULT_TABS` 恰好是 **HOTBAR / SEARCH / OP_BLOCKS / INVENTORY** 这四页（第 176-179 行）。
它们被排除在**节点**之外，但第 144-149 行的边**没有做同样的排除**；而 Guava 的
`MutableGraph#putEdge` 在端点不存在时会**自动补上节点**。于是：

> 你只要写 `withTabsBefore(CreativeModeTabs.HOTBAR)`，HOTBAR 就被这条边**拉回排序图**，
> 参与拓扑排序，把原本「不参与排序」的原版页插到不该出现的位置。

**正解**
整条链锚在**普通原版页**的末尾：`CreativeModeTabs.SPAWN_EGGS`（`CreativeModeTabs.java:59` 定义），
页与页之间用 `withTabsAfter` 串成一条链。本仓库**1.4 定稿后只有一个创造页**，所以只有一条入边：

```
bettergold_tab  .withTabsBefore(SPAWN_EGGS)        // 本模组内容全部合并到这一页，页内用 5 条横幅分区
```

链条整体落在 `spawn_eggs` 之后。多页时代（此前版本）的写法是每页都写一条
`withTabsBefore(SPAWN_EGGS)`、页间再用 `withTabsAfter` 串起来 ——
**每页都有至少一条入边**，拓扑排序才不会把它们甩到别处；页数变了这条纪律不变。

**实测证据**
`build\probe-after-server.log:691-706`（多页时代的归档），`runServer` 探针直接打印
`CreativeModeTabs.tabs()`（即排序后的页列表），共 16 项：

```
 1. minecraft:building_blocks          ...
 9. minecraft:ingredients
10. minecraft:spawn_eggs
11. bettergold:bettergold_materials_tab
12. bettergold:bettergold_tab
13. bettergold:bettergold_food_tab
14. bettergold:bettergold_gear_tab
15. bettergold:bettergold_fd_tab
16. farmersdelight:farmersdelight
```

【实测】1.4 定稿后同一探针的输出（`build\probe-server3.log`）是 **12 项**：
原版 10 项一位不差（`building_blocks` … `spawn_eggs`），第 11 项 `bettergold:bettergold_tab`、第 12 项 `farmersdelight:farmersdelight`。

**注意第 1-10 项里没有 `hotbar` / `search` / `op_blocks` / `inventory`** —— 这正是「默认页被排除在排序图外」的
直接体现；一旦你锚了它们，它们就会出现在这个列表里。

**诚实标注**
「锚 HOTBAR 会把原版页挤到第二页」这个现象当时被观察到，并写在 `bettergold.java:60-63` 的注释里（【记录】），
但**那一轮的日志没有留档**（`build\` 下最早的已排序页清单已经是修好之后的）。
所以：**机制解释是【读源码】，现象本身是【记录】**。想亲手复现，把 `bettergold.java:64` 改成
`.withTabsBefore(CreativeModeTabs.HOTBAR)` 跑一次 `runServer`，对比上面那张列表即可。

**再补一个坑（【读源码】）**
`int vanillaTabs = 10;`（`CreativeModeTabRegistry.java:183`）是 NeoForge 的**硬编码**：它假定注册顺序里前 10 个
非默认页就是原版页，并对它们自动串链（第 195-198 行）。若另一个模组在你之前注册了额外的页，这个 10 就可能对不上。
结论不变：**自己的页一律显式写 `withTabsBefore/After`**，不要依赖「什么都没写就连在最后」那条分支（第 210-211 行）。

## §6 卷动跟随：`scrollOffs` → 首个可见行 的原版公式与字段位置

**现象**
横幅不跟着滚（一直画在同一行），或滚动时**跳一格 / 差一行**，或横幅在某些滚动位置消失。

**字段位置（【读源码】，全在 `net.minecraft.client.gui.screens.inventory.CreativeModeInventoryScreen`）**

| 需要的东西 | 声明位置 | 备注 |
|---|---|---|
| 当前选中的页 | 第 **105** 行 `private static CreativeModeTab selectedTab;` | **static** 字段 → 反射读要传 `null` 作为实例 |
| 卷动位置 0..1 | 第 **109** 行 `private float scrollOffs;` | 屏幕实例字段，**不在 menu 里**（容易找错地方） |
| 可见行数 | 第 **93** 行 `private static final int NUM_ROWS = 5;` | 公式里的 `-5` 就是它 |
| 界面尺寸 | 第 **130-131** 行 `imageHeight = 136; imageWidth = 195;` | |
| 物品格坐标 | 第 **1010** 行 `new ...Slot(CONTAINER, i*9+j, 9 + j*18, 18 + i*18)` | 这是**物品（16×16）**的绘制位置（`renderSlot` 用 `slot.x/slot.y`，`AbstractContainerScreen.java:244-246`）；**18×18 的格子底图**左上角各少 1 像素 ⇒ 物品区左上角 = `(leftPos + 8, topPos + 17)`（像素级核实见 `03` 步骤 7 与 `05` §4.3） |
| 左上角 | `AbstractContainerScreen` 第 **74/78** 行 `protected int leftPos; protected int topPos;` | NeoForge 另暴露 getter：第 **752-753** 行 `getGuiLeft()/getGuiTop()` |

**公式（【读源码】，`ItemPickerMenu` 内部类）**

```java
// 第 1029-1031 行
protected int calculateRowCount() {
    return Mth.positiveCeilDiv(this.items.size(), 9) - 5;
}
// 第 1033-1035 行
protected int getRowIndexForScroll(float scrollOffs) {
    return Math.max((int)((double)(scrollOffs * (float)this.calculateRowCount()) + 0.5), 0);
}
```

这两个方法是 `protected`（在公开内部类 `ItemPickerMenu` 上），外部无法直接调用 → 自己照抄公式即可
（注意 `calculateRowCount()` 可能 ≤ 0，此时首个可见行恒为 0，必须先判掉，否则除零/负数）。

**行 → 物品索引的映射（【读源码】，第 1048-1061 行 `scrollTo`）**

```java
int i = this.getRowIndexForScroll(pos);
for (int j = 0; j < 5; j++) {
    for (int k = 0; k < 9; k++) {
        int l = k + (j + i) * 9;
        if (l >= 0 && l < this.items.size()) CONTAINER.setItem(k + j * 9, this.items.get(l));
        else                                CONTAINER.setItem(k + j * 9, ItemStack.EMPTY);
    }
}
```

⇒ **`menu.getSlot(0).getItem() == items.get(首个可见行 * 9)`**。这条等式是客户端探针最好的交叉校验，
见 `04-验证清单.md` §3。

**实测自检（【实测】，`build\banner-runClient2.log:856-885`）**

```

[TEMP-BANNER] tab=bettergold:bettergold_materials_tab page=materials
              banner=bettergold:textures/gui/creative_sections/materials.png
              scrollOffs=0.33333334 firstVisibleRow=1 items=72 leftPos=116 topPos=52 itemArea=(124, 69)
...

                slot(0,0)=bettergold:gift_gold_ticket items[9]=bettergold:gift_gold_ticket match=true
```

## §7 探针纪律：关服只能调一次 `halt(false)`；`run\` 目录独占

**现象 A（重复关闭）**
探针收尾先 `server.stopServer()` 再 `server.halt(false)`，日志**停在存盘流程里不再推进**，
看起来像卡死 / 存不住盘。前序记录在 `docs\构建与跑测注意事项.md:32-34`（【记录】）。

**根因（【读源码】，`net.minecraft.server.MinecraftServer`）**

```java
// 第 663-672 行：halt 只做一件事 —— 把 running 置 false
public void halt(boolean waitForServer) {
    this.running = false;
    if (waitForServer) { ... this.serverThread.join(); ... }
}

// 第 745-758 行：真正的关闭/存盘在 runServer() 的 finally 里
} finally {
    try {
        this.stopped = true;
        this.stopServer();          // 第 748 行 ← 打 "Stopping server"、存盘、卸载 config
    } catch (Throwable throwable) { ... }
    finally {
        ServerLifecycleHooks.handleServerStopped(this);
        this.onServerExit();
    }
}

// 第 588-590 行：close() 也会再调一次
public void close() { this.stopServer(); }
```

`stopServer()`（第 592-638 行）里依次是 `LOGGER.info("Stopping server")`（597）、`isSaving = true`（599）、
`"Saving players"`（601）、`"Saving worlds"`（606）、存每个维度（约 640 行前后）、最后 `isSaving = false`（638）。

⇒ **额外手动 `stopServer()` 之后 `halt(false)`，关闭流程必然走两遍**（两遍 "Stopping server" + 两遍存盘）。
正确做法是**只调用一次 `halt(false)`**，随后原版自己完成 "Stopping server → 存盘 → 卸载 config"。

**正例（【实测】，一遍干净关闭）**
`build\probe-after-server.log:755-771`：

```
[PROBE14] switch file present -> halt(false)
[minecraft/MinecraftServer]: Stopping server
[minecraft/MinecraftServer]: Saving players
[minecraft/MinecraftServer]: Saving worlds
[minecraft/MinecraftServer]: Saving chunks for level 'ServerLevel[world]'/minecraft:overworld
... （the_end / the_nether）
[CommonHooks/WP]: Gathered mod list to write to world save world
[ThreadedAnvilChunkStorage (world): All chunks are saved] ...
[ThreadedAnvilChunkStorage: All dimensions are saved]
[fml/ConfigTracker/CONFIG]: Unloading configs type SERVER
BUILD SUCCESSFUL in 26s
```

**反例（【实测】+【推断】）**
`build\server-sections5.log` 末尾：探针输出之后**完全没有**关闭日志，Gradle 收场是

```
> Task :runServer FAILED
> Process 'command '...\java.exe'' finished with non-zero exit value -1
BUILD FAILED in 2m 16s
```

这一轮究竟是「重复关闭」还是「被强杀」，日志不足以断定 —— 标【推断】。
但可以确认一条实用结论：**探针收尾异常会让 `runServer` 以非零码结束，不要把 `BUILD FAILED` 一律当成代码错误**；
先看日志有没有走完 "Stopping server → All dimensions are saved"。

**现象 B（`run\` 目录独占）【记录】**
`docs\构建与跑测注意事项.md:14-22`：

- 同时跑两个客户端（或客户端 + 服务端）会抢 `run\logs\latest.log`、`options.txt`、世界文件；
  症状是**卡在 100% 加载不动**，或 `Unable to delete file ... latest.log`。
- 重跑前删 `run\world\session.lock` 与 `run\saves\*\session.lock`。
- **杀进程要精准**：只杀命令行里含 `forgeclientdev` / `forgeserverdev` 的 java 进程；
  不要 `Get-Process java | Stop-Process -Force`，那会连带杀掉 Gradle daemon，写坏配置缓存
  （症状 `Could not load compiled classes for build file ... from cache`，修法 `gradlew --stop` + 删 `.gradle/configuration-cache`）。
- 多人/多代理协作时由协调方逐个发放 `run\` 许可。

**另外两条探针纪律【记录】**

1. **能关掉别人游戏/服务器的能力（`halt`、`System.exit`、`stopServer`）绝不允许进生产代码。**
   曾有一个临时探针在别人客户端进世界时触发 `halt`，直接把对方正在跑的集成服务器关掉，整轮验证作废。
   探针收尾要**整块删除**（不是注释掉），并给出 grep 证据。
2. **探针输出中文会按 GBK 写出**，重定向后按 UTF-8 读会乱码 → 探针把中文转成 `\uXXXX` 再打印。
   本仓库所有探针日志里的 `\u91D1\u5C5E`（金属）、`\u5176\u4ED6\u6750\u6599`（其他材料）就是这么来的 ——
   读日志时用 `[regex]::Unescape()` 或 `ConvertFrom-Json` 风格反解即可。

## §8 构建判读：PowerShell 把 javac 的「注:」记成 `NativeCommandError`，假报 exit 1

**现象**
`.\gradlew.bat build ... 2>&1 | Tee-Object ...`（或任何让 stderr 进 PowerShell 错误流的写法）之后，
pwsh 打印红色的

```
.\gradlew.bat : 注: 某些输入文件使用或覆盖了已过时的 API。
    + CategoryInfo          : NotSpecified: (注: ...:String) [], RemoteException
    + FullyQualifiedErrorId : NativeCommandError
```

看起来构建失败（调用方常把它读成 exit 1），**但 Gradle 其实是成功的**。

**根因**
javac 的提示（弃用 API 之类）写在 **stderr**；PowerShell 把原生命令写进 stderr 的内容一律记成
`NativeCommandError`。这与 Gradle 的退出码无关。

**实测证据**
同一次构建的两个文件（【实测】）：

- `build\_dsh_after_build.err` —— 内容就是上面那段 PowerShell 错误记录（`NativeCommandError` + 被按本地代码页
  写出的「注: …」，读出来是乱码，因为 PowerShell 用了 GBK）；
- `build\_dsh_after_build.log` —— 同一轮构建：

  ```
  > Task :compileJava
  ...
  BUILD SUCCESSFUL in 3s
  4 actionable tasks: 2 executed, 2 up-to-date
  ```

**修法**

1. 判断成败**只看** Gradle 输出的 `BUILD SUCCESSFUL` / `BUILD FAILED`，或 `$LASTEXITCODE`；
   不要看 pwsh 有没有红字。
2. 想让日志干净：把 stderr 单独重定向到文件（`2>build\x.err`）后**单独读**，或者加 `--console=plain` 并只看 stdout。
3. 同理：`git push` 的进度信息也走 stderr，出现红色 `NativeCommandError` 不代表失败，看 `$LASTEXITCODE`。

## §9 「只读 JSON / 源码」**不算验证**

**事故（【记录】，`docs\构建与跑测注意事项.md:59-61`）**
曾经读了掉落表 JSON 里 `chance=0.36`，就宣称修好了，实际那份表**根本没有被加载**（JSON 解析失败），
玩家打半天不掉东西。

**纪律**
任何**数据文件**（JSON / 标签 / 配方 / 模型 / 语言）都必须让游戏**真的加载它**，并留下日志证据；
任何**渲染**都必须让渲染路径真的执行、并留下坐标日志（能截图更好）。
「我读了源码，逻辑是对的」只能证明「逻辑是对的」，不能证明「这段逻辑跑起来了」。

**本文档相关的落地做法（本仓库实际用过）**

| 要验证的东西 | 怎么让它「真的跑起来」 | 日志证据 |
|---|---|---|
| 分区排布/行号/不丢物品 | `runServer` + 在服务器启动后直接读**已是成品**的 `CreativeModeTab#getDisplayItems()` 做统计（不是自己重算） | `build\server-sections5.log`（多页时代）；1.4 定稿后（一页 5 分区）是 `build\probe-server3.log:525` + `:532-542` 与 `build\so-server3.log:528-536`（`displayItems=274 nonempty=206 … sections=5`，5 条横幅行全空） |
| 创造页排序 | `runServer` + 打印 `CreativeModeTabs.tabs()` | `build\probe-after-server.log:691-706` |
| 横幅绘制坐标与卷动跟随 | `runClient` + 在渲染事件里打印 `leftPos/topPos/itemArea/首可见行/每行是否整行空` | `build\banner-runClient2.log:856-885` |
| 别名懒绑定是否指向同一个注册项 | 运行时探针比较 `AllItems.X.get() == AllMetals.Y.ingot.get()`（35/35 相同） | `docs\1.4-进度与交接.md:25`（【记录】） |

**汇报纪律**
把「实机验证过的数字」与「仅编译 / 仅读源码」**分开写**。本文件夹每个结论都带等级标注，就是这个原因。

## §10 附：文件与编码（会浪费你半天时间的那类问题）

【记录】，`docs\构建与跑测注意事项.md:36-43`：

1. **一律无 BOM。** Windows PowerShell 5.1 的 `Set-Content -Encoding UTF8` **会写 BOM**，
   JSON 与 `.java` 都可能因此出问题。用编辑工具，或
   `[System.IO.File]::WriteAllText($path, $text, (New-Object System.Text.UTF8Encoding($false)))`。
2. **不要用 `Get-Content` / `Set-Content` 做文本替换**：会把中文注释变成乱码（本仓库中过两次，只能靠 git 恢复）。
   必须用 PowerShell 时走 `ReadAllText` / `WriteAllText` + 显式 UTF-8。
3. **删代码块按「标记 + 锚点」成对定位**，不要用行数算术（曾多切 4 行，切出多余右括号，构建失败）。
4. 本仓库 `.java` 多为 CRLF；用字符串拼多行锚点时注意 `` "`r`n" ``。本 `docs\创造页分区栏目-参考实现\` 下的
   Markdown 统一用 **LF**（跨平台好读）。
