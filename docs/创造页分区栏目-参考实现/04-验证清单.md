# 04 - 验证清单

> **本文档解决什么问题：** 给一份可以直接照抄的验证方案 —— 探针该打印哪些量、怎么交叉校验卷动公式、
> `runServer` 与 `runClient` 各自要确认什么、**哪些东西只能靠人眼**。
> **适合谁看：** 实现写完了、准备验收（或正在 debug「横幅没出来」）的人。

**总原则（先读这三条）**

1. **只读 JSON / 只读源码不算验证。** 必须让游戏真的加载（创造页真的构建出物品列表）、渲染路径真的执行，
   并留下日志。`02` §9 有事故案例。
2. **探针必须整块删除。** 收尾时删掉探针代码 + 开关文件，并给出 grep 证据。
   **任何能关服/关客户端的调用（`halt`、`stopServer`、`System.exit`）绝不允许进生产代码。**
3. **`run\` 目录是独占资源**：同一时刻只跑一个游戏进程；跑前删 `session.lock`；
   关服**只调一次 `halt(false)`**（`02` §7）。

## §1 服务端探针要打印哪些量

探针挂在 `ServerStartedEvent`（或 `FMLCommonSetupEvent` 之后的任意服务端时机），
**直接读已经构建好的 `CreativeModeTab#getDisplayItems()`** —— 不要去自己重算布局，
否则你只是在验证自己的算法而不是验证游戏里的真实状态。

### 1.1 每一页打印一行汇总

> **1.4 定稿后的现状**：本模组只有**一个**创造页、页内 **5 个分区**（材料/建筑/食物/装备/乐事），
> 所以汇总行只有一条、分区行只有 5 条（`SECTION_ROWS` = 5）。下面这段是**多页时代**的【实测】归档，
> 保留下来是为了说明「一行汇总要打哪些量」，不要再拿它的 5 页数字对现在的仓库。

| 打印项 | 含义 | 期望 |
|---|---|---|
| `candidates` | 该页候选物品数 | 与你准备的一致 |
| `slots`（= `getDisplayItems().size()`） | 显式物品列表长度（含空格子） | `= 9 + Σ size + Σ pad`（样例：材料页 65） |
| `nonempty` | 其中非空格子数 | `== candidates`（没有物品被吞） |
| `blank spacer` | 空格子数 | `= slots − nonempty`（样例：材料页 31） |
| `buckets` | 桶（分区）数量 | `== 该页 Slot 数量`（样例：材料页 3） |
| `lost` | `candidates − nonempty` | **必须为 0** |

样例（【实测】`build\server-sections5.log`）：

```
== tab materials (bettergold:bettergold_materials_tab) : candidates 34 / slots 65 (nonempty 34, blank spacer 31) / buckets 34 ==
== tab blocks    (bettergold:bettergold_tab)           : candidates 66 / slots 103 (nonempty 66, blank spacer 37) / buckets 66 ==
== tab food      (bettergold:bettergold_food_tab)      : candidates 28 / slots 67 (nonempty 28, blank spacer 39) / buckets 28 ==
== tab gear      (bettergold:bettergold_gear_tab)      : candidates 47 / slots 65 (nonempty 47, blank spacer 18) / buckets 47 ==
== tab fd        (bettergold:bettergold_fd_tab)        : candidates 31 / slots 93 (nonempty 31, blank spacer 62) / buckets 31 ==
```

【实测】1.4 定稿（一页 5 分区）之后，同一条探针打印的是**一行**：

```
== tab bettergold:bettergold_tab displayItems=274 nonempty=206 blankSpacer=68 candidates=206 bucketItems=206 sections=5 ==
```

> 注意样例里 `buckets` 那一栏打的是「桶内物品数之和」，与 `candidates`、`nonempty` 相等 —— 这正是下面说的三方相等。
> （打印时把它标成 `buckets` 有歧义，建议你改叫 `bucketItems` 或 `bucketsSum`，更不容易看错。）

### 1.2 每一个分区打印一行

| 打印项 | 含义 | 期望 | 样例 |
|---|---|---|---|
| `secN` | 分区序号（= 显示顺序） | 从 1 递增 | `sec1` |
| 释词 | 分区标题（**中文转义成 `\uXXXX` 打印**，避免 GBK 乱码，见 `02` §7） | 与 `Slot` 定义一致 | `\u5176\u4ED6\u6750\u6599`（其他材料） |
| `firstItemRow` | 该分区**首个物品**所在行号（`SECTION_ROWS` 的值） | 首区恒为 1 | `1` |
| `bannerRow` | 横幅行 = `firstItemRow − 1` | 首区恒为 0 | `0` |
| `bannerAllBlank` | `bannerRow` 那一行**是否整行空格子** | **必须 `true`**（渲染端唯一依赖的不变量 I2） | `true` |
| `headOk` | 该区首物品与预期一致（逐页写死几个期望 id 或者在探针里按规则重算） | `true` | `true` |
| `size` | 该分区物品数 | 与你的规则一致 | `9` |
| `head` | 前 5 个物品 id | 人眼扫一眼顺序对不对 | `[bettergold:mixed_crystal_pile …]` |
| `firstItemAtRowN=true` | （可选）交叉确认「第一个物品确实在第 N 行」 | `true` | `true` |

样例（【实测】`build\server-sections3.log`，用的是另一版探针字段名，语义相同）：

```
[DBG]    sec1 \u4EA4\u6613\u91D1\u5546\u4EBA\u76F8\u5173 bannerRow=0 bannerAllBlank=true firstItemAtRow1=true size=5
         head=[bettergold:gift_gold_ticket bettergold:treasure_gift_box bettergold:curio_box bettergold:idol_gift_box bettergold:gourmet_box]
[DBG]    sec2 \u91D1\u5C5E bannerRow=2 bannerAllBlank=true firstItemAtRow3=true size=20
[DBG]    check: nonempty 34 vs candidates 34 vs buckets 34 -> OK none lost ; firstSectionBannerRow=0 (expect 0)
```

最后那行 `nonempty 34 vs candidates 34 vs buckets 34 -> OK none lost` 就是**三方相等**的断言：
「显式物品列表里的非空格子数」「候选物品数」「所有桶的物品数之和」三者相等 ⇒ **一件都没丢、也没有重复放入**。

### 1.3 三方相等怎么写

```java
int nonempty   = (int) tab.getDisplayItems().stream().filter(s -> !s.isEmpty()).count();
int candidates = candidatesSupplier.get().size();
int bucketSum  = buckets.stream().mapToInt(b -> b.items().size()).sum();
LOGGER.info("[probe] check: nonempty {} vs candidates {} vs buckets {} -> {}",
        nonempty, candidates, bucketSum,
        (nonempty == candidates && candidates == bucketSum) ? "OK none lost" : "MISMATCH");
```

> **不要**用「非空格子数 == 桶数」这种写法（样例日志里的 `buckets` 其实是「桶内物品数之和」，
> 字段名容易误导 —— 我们的探针就是踩过这个命名的坑）。

## §2 `runServer` 要确认什么

### 2.1 创造页排序表（**先做这一步**）

打印 `CreativeModeTabs.tabs()`（需要访问变换器，或像本仓库一样用探针里已有的访问路径），
确认自己的页都在 `minecraft:spawn_eggs` **之后**，并且顺序与你的 `withTabsAfter` 链一致。

【实测】`build\probe-after-server.log:691-706`（多页时代的归档，本模组当时有 5 页）：

```
[PROBE14] == sorted creative tabs: 16 ==
[PROBE14]   1. minecraft:building_blocks      ...      9. minecraft:ingredients
[PROBE14]  10. minecraft:spawn_eggs
[PROBE14]  11. bettergold:bettergold_materials_tab
[PROBE14]  12. bettergold:bettergold_tab
[PROBE14]  13. bettergold:bettergold_food_tab
[PROBE14]  14. bettergold:bettergold_gear_tab
[PROBE14]  15. bettergold:bettergold_fd_tab
[PROBE14]  16. farmersdelight:farmersdelight
```

【实测】1.4 定稿（内容合并成**一页**）之后，`build\probe-server3.log` 里同一探针的输出：

```
[SECPROBE] == sorted creative tabs: 12 ==
[SECPROBE]   1. minecraft:building_blocks      ...      9. minecraft:ingredients
[SECPROBE]  10. minecraft:spawn_eggs
[SECPROBE]  11. bettergold:bettergold_tab          ← 本模组只剩这一页
[SECPROBE]  12. farmersdelight:farmersdelight      ← 联动模组自己的页仍在
```

**同时确认前 10 项里没有 `hotbar` / `search` / `op_blocks` / `inventory`** ——
如果有，说明你（或某个模组）锚了 `DEFAULT_TABS` 里的页，把原版默认页拉进了排序图（`02` §5）。

### 2.2 真实物品列表（不是自己重算的）

`runServer` 里读的是**已经构建好的** `CreativeModeTab#getDisplayItems()`：

```
[PROBE14] tab materials (bettergold:bettergold_materials_tab) displayItems=65 nonempty=34
```

`displayItems` 与 §1.1 的 `slots` 是同一个数（65）。**这个数字是「游戏真的构建出来的」**，
所以它同时证明了：生成器跑了、`getDisplayItems()` 覆写被调用了、空行真的插进去了。

> **【实测】踩坑提醒（1.4 验证时发现）**：专用服务器在 `ServerStartedEvent` 时**还没有**构建过任何页的内容，
> 此时读 `getDisplayItems()` 会得到 **0**（不是"丢物品"，是"还没构建"）。
> 想读到真实列表，探针必须先让原版走一次构建：
> ```java
> CreativeModeTabs.tryRebuildTabContents(server.getWorldData().enabledFeatures(), false, server.registryAccess());
> ```
> 这条路与客户端进创造界面时走的完全相同（`buildAllTabContents` → `EventHooks.onCreativeModeTabBuildContents`
> → 你的 `displayItems` 生成器），所以读到的仍是「游戏真实构建出来的」结果，而不是自己重算的。

### 2.3 `SECTION_ROWS` 全表

打印整张表并数一下键数：

```
[PROBE14] == section rows (SECTION_ROWS) total=16 ==
[PROBE14]   row materials|\u5176\u4ED6\u6750\u6599 -> 1
[PROBE14]   row materials|\u4EA4\u6613\u91D1\u5546\u4EBA\u76F8\u5173 -> 3
[PROBE14]   row materials|\u91D1\u5C5E -> 5
...
```

期望：`total == 所有分区的数量之和`（多页时代样例 = 3+3+3+2+5 = 16）。
键数偏少 ⇒ 释词重复导致互相覆盖（`01` §3）。

【实测】1.4 定稿（一页 5 个横幅分区）之后，这张表恒为 **5** 条，键就是分区 key（不再带页前缀、也不拼释词）：

```
[SECPROBE] SECTION_ROWS total=5 (expect 5 with FD / 4 without)
[SECPROBE]   sec1 key=materials label=材料 size=34 firstItemRow=1  bannerRow=0  bannerAllBlank=true
[SECPROBE]   sec2 key=blocks    label=建筑 size=66 firstItemRow=6  bannerRow=5  bannerAllBlank=true
[SECPROBE]   sec3 key=food      label=食物 size=28 firstItemRow=15 bannerRow=14 bannerAllBlank=true
[SECPROBE]   sec4 key=gear      label=装备 size=47 firstItemRow=20 bannerRow=19 bannerAllBlank=true
[SECPROBE]   sec5 key=fd        label=乐事 size=31 firstItemRow=27 bannerRow=26 bannerAllBlank=true
```

### 2.4 `runServer` 收尾

一遍干净的关闭长这样（【实测】`build\probe-after-server.log:755-771`）：

```
[PROBE14] switch file present -> halt(false)
Stopping server → Saving players → Saving worlds → Saving chunks for level ... →
All dimensions are saved → Unloading configs type SERVER
BUILD SUCCESSFUL in 26s
```

若出现 `BUILD FAILED ... non-zero exit value -1` 且**没有** "Stopping server"，
先怀疑探针收尾（重复关闭被强杀），不要先怀疑业务代码（`02` §7）。

## §3 客户端探针要打印哪些量

客户端探针挂在渲染事件里（我们自己那个 `ScreenEvent.Render.Post` 里加一段临时打印最省事）。
**每帧都打会淹掉日志** —— 加节流（例如「值变了才打」或「前 200 帧不打」）。

### 3.1 一帧一行上下文

```java
LOGGER.info("[probe] tab={} page={} banner={} scrollOffs={} firstVisibleRow={} items={} leftPos={} topPos={} itemArea=({},{})",
        tabId, page.tabKey(), page.banner(), scrollOffs, firstVisibleRow,
        menu.items.size(), leftPos, topPos, leftPos + 8, topPos + 17);
```

样例（【实测】`build\banner-runClient2.log:858`）：

```
[TEMP-BANNER] tab=bettergold:bettergold_materials_tab page=materials
  banner=bettergold:textures/gui/creative_sections/materials.png
  scrollOffs=0.33333334 firstVisibleRow=1 items=72 leftPos=116 topPos=52 itemArea=(124, 69)
```

**为什么要一起打 `leftPos/topPos` 和 `itemArea`**：`itemArea = (leftPos+8, topPos+17)` 这一行日志
把「8/17 偏移」这件事变成可核对的事实；样例里 `116+8=124`、`52+17=69` ✓。

### 3.2 交叉校验：`slot(0,0) == items[首可见行 × 9]`

这是**最有价值的一条**：它一次性验证「卷动公式」+「items → 槽位映射」两件事。

```java
int firstVisibleRow = firstVisibleRow(menu, scrollOffs);
ItemStack slot00 = menu.getSlot(0).getItem();
ItemStack expect = menu.items.get(firstVisibleRow * 9);
LOGGER.info("[probe] cross-check firstVisibleRow={} slot(0,0)={} items[{}]={} match={}",
        firstVisibleRow, idOf(slot00), firstVisibleRow * 9, idOf(expect),
        ItemStack.matches(slot00, expect));   // 或者只比 item + count
```

样例（【实测】`build\banner-runClient2.log:880`）：

```
[TEMP-BANNER]   cross-check firstVisibleRow=1
                slot(0,0)=bettergold:gift_gold_ticket items[9]=bettergold:gift_gold_ticket match=true
```

**依据（【读源码】）**：原版 `ItemPickerMenu#scrollTo`（`CreativeModeInventoryScreen.java:1048-1061`）里
`int l = k + (j + i) * 9;` + `CONTAINER.setItem(k + j * 9, items.get(l))`，其中 `i` = 首可见行。
所以 `k=0, j=0` 时槽位 0 的内容就是 `items[首可见行 × 9]`。

**注意**：`match=false` 不一定是 bug —— 如果 `items` 里那一位是 `ItemStack.EMPTY`（空行），
两边都是空也算一致。用「物品相同 或 两者都空」判等，别用 `==`。

### 3.3 `scrollOffs` 多个取值的公式自检

把 `scrollOffs` 手动喂几个值进你的公式，打印结果，与原版公式对账：

```java
for (float s : new float[] {0.0F, 0.25F, 0.5F, 0.75F, 1.0F}) {
    LOGGER.info("[probe] formula scrollOffs={} -> firstVisibleRow={}", s, firstVisibleRow(menu, s));
}
```

样例（【实测】`build\banner-runClient2.log:881-885`，该帧 `items=72 ⇒ rowCount = ceil(72/9) − 5 = 3`）：

```
formula scrollOffs=0.0  -> firstVisibleRow=0     // 0.0×3+0.5 = 0.5 → (int)0
formula scrollOffs=0.25 -> firstVisibleRow=1     // 0.25×3+0.5 = 1.25 → 1
formula scrollOffs=0.5  -> firstVisibleRow=2     // 0.5×3+0.5  = 2.0  → 2
formula scrollOffs=0.75 -> firstVisibleRow=2     // 0.75×3+0.5 = 2.75 → 2   ← 注意：不是 3
formula scrollOffs=1.0  -> firstVisibleRow=3     // 1.0×3+0.5  = 3.5  → 3
```

**手算验证**：公式是 `max((int)(scrollOffs × rowCount + 0.5), 0)`（原版 `CreativeModeInventoryScreen.java:1033-1035`）。
`0.75` 那一行得 2 而不是 3，是 `(int)` **截断**（不是四舍五入到 3）—— 这正是容易写错的地方：
不要用 `Math.round`，要用 `(int)(x + 0.5)`。**如果五个值里有一个对不上，你的公式就写错了。**

### 3.4 每个可见行是否整行空

```
[TEMP-BANNER]   visibleRow 0 empty=false
[TEMP-BANNER]   visibleRow 1 empty=true
[TEMP-BANNER]   visibleRow 2 empty=false
[TEMP-BANNER]   visibleRow 3 empty=false
[TEMP-BANNER]   visibleRow 4 empty=false
```

（【实测】`build\banner-runClient2.log:875-879`）
**用途**：和 §3.5 的横幅行判定对账 —— 横幅画在第 1 可见行，而第 1 行确实 `empty=true` ✓。

### 3.5 每个分区的横幅行判定

```
[TEMP-BANNER]   key=materials|\u91D1\u5C5E mine=true anchorRow=2 -> row=1 screenX=124 screenY=87
[TEMP-BANNER]   key=materials|\u5176\u4ED6\u6750\u6599 mine=false anchorRow=0 -> row=-1 screenX=124 screenY=-1
```

（【实测】`build\banner-runClient2.log:872-874`）
**要看的**：`mine`（这一页是不是当前选中页）、`anchorRow`（记录值 − 首可见行）、
`row`（自适应判定结果，`-1` = 不画）、`screenX/screenY`（最终像素坐标）。
`screenY = topPos + 17 + row*18 = 52 + 17 + 1*18 = 87` ✓。

## §4 `runClient` 要确认什么

| 序号 | 确认项 | 判据 |
|---|---|---|
| 1 | 创造界面里出现了横幅条、释词正确 | 人眼（见 §6） |
| 2 | 横幅**没有盖住任何物品** | 每帧的 `isRowEmpty(横幅行) == true`，可在探针里加一条断言 |
| 3 | 滚动时横幅跟随 | 缓慢滚动，横幅应平滑地上下移动，到边界时消失（`row = -1`） |
| 4 | **别的标签页没有被画上横幅** | 切到原版页、再切到你自己的别的页，确认只有对应页有横幅（前置判断是否写全，见 `03` 步骤 6） |
| 5 | 切页/搜索框输入不崩 | 在搜索框里输入、清空、切页各来几次；反射失败必须静默降级（`03` 步骤 6 纪律 1） |
| 6 | 日志里没有 `blitSprite` 相关的缺图（紫黑格不会有日志，只能靠人眼） | 人眼 + 对照 `02` §2 |
| 7 | 装了别的模组时横幅不错位 | 装几个也会往创造页插物品的模组（例如 JEI/REI 一类不影响；真正有影响的是会订阅 `BuildCreativeModeTabContentsEvent` 的模组），看长度守卫是否触发回退（回退后应**没有**横幅，而不是错位） |

## §5 可照抄的运行方式

```powershell
# 0) 清残留（run\ 独占；不要一把梭杀所有 java —— 会杀到 Gradle daemon，见 02 §7）
Get-Process java -ErrorAction SilentlyContinue |
    Where-Object { $_.CommandLine -match 'forgeclientdev|forgeserverdev' } |
    Stop-Process -Force
Remove-Item -Force run\world\session.lock, run\saves\*\session.lock -ErrorAction SilentlyContinue

# 1) 服务端探针（把 stderr 单独放，避免 PowerShell 把 javac 的「注:」记成 NativeCommandError，见 02 §8）
.\gradlew.bat runServer --console=plain 2>build\probe-server.err >build\probe-server.log
Select-String build\probe-server.log -Pattern 'PROBE|DBG|CHECK|BUILD SUCCESSFUL|BUILD FAILED'

# 2) 客户端探针（同样把 stderr 分开）
.\gradlew.bat runClient --console=plain 2>build\probe-client.err >build\probe-client.log
Select-String build\probe-client.log -Pattern 'TEMP-|PROBE|cross-check|formula|visibleRow'
```

**读带 `\uXXXX` 的日志**（探针为避开 GBK 乱码才这么打印，`02` §7）：

```powershell
# 把日志里的 \uXXXX 还原成人能读的中文
(Get-Content build\probe-server.log -Raw -Encoding UTF8) `
  -replace '\\u([0-9a-fA-F]{4})', { [char][Convert]::ToInt32($_.Groups[1].Value, 16) }
```

**探针收尾（必做）**

```powershell
# 1) 整块删除探针代码（不是注释掉）
# 2) 删开关文件
Remove-Item -Force run\*-probe.enabled -ErrorAction SilentlyContinue
# 3) 给出 grep 证据：应当零命中
Select-String -Path src\main\java\**\*.java -Pattern 'TEMP-|PROBE|halt\(|stopServer\('
```

## §6 只能靠人眼的部分

以下**没有任何自动手段能替代**（截图也只能证明「当时那一眼」，不能证明手感）：

| 项目 | 为什么自动不了 | 怎么验 |
|---|---|---|
| **横幅配色与整体观感** | 「好看」是主观判断；贴图和浅色背景会不会糊在一起，程序看不出来 | 在创造界面逐个页看；分别在白天/夜晚界面背景（创造界面本身没有昼夜差，但显示器的伽马不同）下看一眼 |
| **释词位置与字号** | 释词压在横幅的花纹上是否可读、左右留白是否舒服 | 用「最长的一个释词」（例如「万坚金放置食物」）和「最短的」（例如「种子」）各看一次；**文字长度差很大时底方块宽度会不会难看**，只能眼睛判 |
| **滚动跟随的手感** | 横幅跟着滚会不会「跳」、边界处闪现/消失是否突兀，是帧序列的连续体验 | **缓慢**滚动（不要滚轮一大格一大格）从顶到底走一遍，注意横幅在 `row` 从 4 → −1 那一瞬间的表现 |
| **不同 GUI 缩放（`guiScale`）下的显示** | 缩放变化会改变像素对齐，可能导致 1 像素错位或模糊 | 在视频设置里把 GUI 缩放改成 自动/2/3/4 各看一次；尤其注意 `blit` 的贴图在非整数缩放下是否发虚 |
| **窗口尺寸/宽高比变化** | `leftPos/topPos` 是居中的，窄窗口下界面位置会变 | 拉大/缩小窗口各看一次，确认横幅仍然贴在物品区左上角 |
| **装了其它模组后的观感** | 物品数量变化让分区变长/变短，横幅密度是否还合适 | 装几个大模组后再看一遍创造页 |
| **滚动条的可用性** | 插入空行使物品列表变长 ⇒ 滚动条行程也变长，滚到手酸不酸 | 自己滚一遍；如果太长，考虑减少分区或缩短区间的空行（只能牺牲观感，没有两全方案） |

> **建议**：人眼验收时**同时开着探针日志**（只看关键几行）。这样一旦觉得「哪里不对」，
> 立刻能对照 `screenY / bannerRow / firstVisibleRow` 判断是算错了还是纯主观不满。
