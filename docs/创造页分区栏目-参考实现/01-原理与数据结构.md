# 01 - 原理与数据结构

> **本文档解决什么问题：** 把「分区横幅」背后的数据模型与算法讲清楚 —— 一个分区怎么描述、物品怎么归类、
> 「补满当前行再空一整行」到底怎么算、`SECTION_ROWS` 里存的到底是哪一行。
> **适合谁看：** 准备自己写排布逻辑的人。读完应当能在不看任何参考实现的情况下把算法重写一遍。

本文所有类型名都是**我们这套实现**里的名字（可自由改名），语义与 1.21.1 的原版类型无关，
唯一需要对齐的是 `net.minecraft.world.item.CreativeModeTab` / `ItemStack`。

---

## 一、数据模型总览

四个概念，一层套一层：

> **1.4 定稿后的本仓库现状**：只有**一个**创造页，页内 **5 个分区**（材料 / 建筑 / 食物 / 装备 / 乐事），
> 所以 `SECTION_ROWS` 的键就是**分区 key**（`materials` / `blocks` / …，恒 5 条），
> `Slot` 退化成「分区**内部**的排列规则」（先到先得地决定先放哪一段），
> 由 `CreativeTabSections#ordered` 首尾相接成该分区唯一的连续列表（不插横幅、不插空行）。
> 下面这张图是**通用形态**（多分区时 key 需要带上页前缀，例如 `"标签页key|释词"`）。

```
Slot（分区声明）            释词 + 归属判定（Predicate<ItemStack>）
   │  按顺序、先到先得地把候选物品分进去
   ▼
Bucket（分区 / 桶）         释词 + 该分区排好序的物品列表
   │  layout()：物品 + 空行 排成最终列表，同时记录每个分区的行号
   ▼
List<ItemStack>（显式物品列表）  含 ItemStack.EMPTY 作为空格子；长度不一定是 9 的倍数
   │  渲染时按 SECTION_ROWS 找到空行
   ▼
SECTION_ROWS：Map<String,Integer>    key = 分区标识（本仓库 = 分区 key："materials"…），value = 该分区首个物品所在行（0 基）

Placement（排序键）          (分区 Kind, 金属位次, 区内位次) —— 只用于桶内排序
```

对应到本仓库的文件：

| 概念 | 文件 | 具体类型 |
|---|---|---|
| `Slot`（分区内部的一段顺序规则） | `material\CreativeTabSections.java` | `record Slot(String title, Predicate<ItemStack> test)` |
| 分区注册表（key / 释词 / 横幅 / 候选物品） | `material\CreativePageSections.java` | `record Section(String key, int order, String label, ResourceLocation banner, List<Slot> rules, Supplier<List<ItemStack>> candidates)` |
| `Bucket` | `material\CreativeSections.java` | `record Bucket(String key, String label, List<ItemStack> items)` |
| `Placement` / `Kind` | `material\CreativeSections.java` | `enum Kind` + `record Placement(Kind kind, int metalRank, int slot)` |
| `SECTION_ROWS` / `layout()` | `material\CreativeSections.java` | `LinkedHashMap<String,Integer>` + 静态方法 |
| 补空行的标签页 | `material\SectionedCreativeTab.java` | `class SectionedCreativeTab extends CreativeModeTab` |

## 二、`Slot`：释词 + 归属判定

一个 `Slot` 就是一句声明：「释词是 X 的物品，判定条件是 P」。用 `Predicate<ItemStack>` 而不是物品列表，
目的见 §6。

```java
public record Slot(String title, Predicate<ItemStack> test) {}
```

分桶是**先到先得**：每件候选物品只会进**第一个** `test` 为真的分区，进了就标记为已取走。

```java
boolean[] taken = new boolean[items.size()];
for (Slot slot : slots) {
    for (int i = 0; i < items.size(); i++) {
        if (taken[i]) continue;
        if (!slot.test().test(items.get(i))) continue;
        taken[i] = true;          // 只进第一个命中的分区
        // ...归类
    }
}
```

**由此产生一条硬性纪律：兜底判定（`stack -> true`）只能放在 `Slot` 列表的最后一位。**
如果放在第一位，它会把整页物品全部吃进第一个桶，后面的分区全空。
本仓库踩过这个坑，`CreativeTabSections.java:87-95` 的注释把它写在了明处：

> 材料页最初的写法是「其他材料 = 兜底」，于是「交易金商人相关」「金属」两个桶永远为空。
> 改成**正面判定**「既不是交易金商人相关物、也不是金属物品」之后，三个分区合起来仍然恰好覆盖全部物品，
> 一件都不会丢。

同理，最后一位的兜底分区如果没人命中，它就是「其他」桶 —— 这保证了**任何物品都不会因为
「规则没写全」而被丢掉**（不变量 I3，见 §7）。反过来，也正因为有兜底，**你不应该**依赖
「桶大小之和 == 候选数」来发现规则漏洞：它永远是相等的。想查规则漏洞，要打印每个桶的**首物品**
（见 `04-验证清单.md`）。

## 三、`Bucket`：分区 + 物品

```java
public record Bucket(String key, String label, List<ItemStack> items) {}   // 本仓库 1.4 定稿的形态
// 通用形态也可以只带释词：record Bucket(String title, List<ItemStack> items) {}
```

- `key` 是 **`SECTION_ROWS` 的键**（本仓库 = 分区 key：`materials` / `blocks` / `food` / `gear` / `fd`），
  渲染端用它反查该分区的**横幅贴图与释词**（`CreativePageSections.byKey`）。所以 key 必须唯一，
  否则两条记录会互相覆盖、横幅少画一条。
- `label` 是**横幅上的释词**（材料 / 建筑 / 食物 / 装备 / 乐事）。释词只要求「人看得懂」，
  不再需要充当 map 键 —— 这也是 1.4 把「组 + 分区」两层压平成「一页 5 个分区」之后省掉的一层。
- `items` 必须是**已排好序**的（§5）、**连续**的一条列表（分区内部不再分段插空行），且**不得含空格子**
  —— 空行是 `layout()` 的职责。
- `Bucket` 是 `record`，`items()` 是不可变列表，方便在生成器与渲染之间传递而不怕被改。

## 四、分区枚举与展示顺序

分区「种类」用枚举表示（我们的名字）：

```java
public enum Kind {
    METAL_MATERIALS,   // 材料页：金属（核心材料 / 原料 / 锭 / 粒 / 模板）
    METAL_BLOCKS,      // 建筑方块页：金属块
    METAL_BUILDING,    // 建筑方块页：金属建材（砖块…灯笼）
    METAL_GEAR         // 装备与工具页：金属装备（剑…靴子）
}
```

**关键区分，别搞混：**

| 顺序 | 由谁决定 | 说明 |
|---|---|---|
| **页内分区的展示顺序** | 该页的 `List<Slot>` 顺序 | 这才是横幅从前到后的顺序。例：材料页 = 其他材料 → 交易金商人相关 → 金属 |
| **同一个桶内金属物品之间的顺序** | `Placement.sortKey()`，其中 `Kind.ordinal()` 占最高位 | 防御性设计：正常情况一个桶里只有一个 `Kind`（因为分区本身的判定已经按 Kind 分开了），最高位基本不参与比较 |

也就是说，**`Kind` 的枚举顺序会影响桶内排序，但不决定横幅顺序**。如果你把「金属建材」的 Slot 排在
「金属块」前面，横幅顺序就是建材在前 —— 与枚举里 `METAL_BLOCKS` 写在前面无关。

## 五、`layout()`：补满当前行 + 再空一整行

这是整个效果的算法核心。目标：**让每个分区都从新的一行开始，并且在它上面留出恰好一整行空格子**。

### 5.1 规则

```java
public static List<ItemStack> layout(String tabKey, List<Bucket> buckets) {
    List<ItemStack> out = new ArrayList<>();
    SECTION_ROWS.keySet().removeIf(k -> k.startsWith(tabKey + "|"));   // 本页旧记录先清掉

    // ① 列表开头先补一整行空格子
    for (int i = 0; i < 9; i++) out.add(ItemStack.EMPTY);

    for (int b = 0; b < buckets.size(); b++) {
        Bucket bucket = buckets.get(b);
        // ② 在加入本区物品「之前」取样，记下本区首个物品所在行
        SECTION_ROWS.put(tabKey + "|" + bucket.title(), out.size() / 9);

        out.addAll(bucket.items());

        if (b == buckets.size() - 1) break;          // ③ 最后一区之后不补，避免尾部一大片空
        int used = bucket.items().size() % 9;
        int pad  = (9 - used) % 9 + 9;               // ④ 补满当前行（0~8 个）+ 再空一整行（9 个）
        for (int i = 0; i < pad; i++) out.add(ItemStack.EMPTY);
    }
    return out;
}
```

### 5.2 三个非显然的点

**① 开头必须补一整行空格子。** 横幅画在分区物品的**上面那一行**。第一个分区上方本来什么都没有，
不补这一行，第一个分区的横幅就没有地方画。于是：

> **每页第一个分区的 `SECTION_ROWS` 值恒为 1**（第 0 行是它的横幅行），其余分区也是
> 「横幅行 = 记录值 − 1」。

**② 取样必须在加入本区物品之前。** 否则记下来的是「本区最后一个物品的下一行」，差一整区。

**③ `pad` 一定 ≥ 9。** `(9-used)%9` 是「补满当前行」，`+9` 是「再空一整行」。
如果本区物品数正好是 9 的倍数，`used == 0`，则 `pad = 0 + 9 = 9` —— 仍然恰好空一整行，
不会多出一个「空行 + 空行」。这是这个公式比 `9 - used` 好的地方。

### 5.3 算一遍（【实测】材料页）

数据来自 `build\server-sections5.log` 的探针输出（仓库根为基准）：

```
== tab materials (bettergold:bettergold_materials_tab) : candidates 34 / slots 65 (nonempty 34, blank spacer 31) / buckets 34 ==
   sec1 其他材料          firstItemRow=1 bannerRow=0 bannerAllBlank=true headOk=true size=9
   sec2 交易金商人相关    firstItemRow=3 bannerRow=2 bannerAllBlank=true headOk=true size=5
   sec3 金属              firstItemRow=5 bannerRow=4 bannerAllBlank=true headOk=true size=20
   check: nonempty 34 vs candidates 34 vs buckets 34 -> OK none lost
```

| 行 | 内容 | 怎么来的 |
|---|---|---|
| 0 | 9 个空格子 | 规则 ① |
| 1 | 其他材料（9 个） | `SECTION_ROWS["materials\|其他材料"] = 1`；横幅行 = 0 |
| 2 | 9 个空格子 | `size % 9 == 0` → `pad = 0 + 9 = 9` |
| 3 | 交易金商人相关（5 个）+ 4 个空格子（补满行 3） | `SECTION_ROWS = 3`；横幅行 = 2 |
| 4 | 9 个空格子 | `pad = (9-5)%9 + 9 = 4 + 9 = 13`（4 补满行 3，9 是行 4） |
| 5~7 | 金属（20 个，占 3 行） | `SECTION_ROWS = 5`；横幅行 = 4；最后一区不补 |

总长度 `9 + 9 + 9 + 5 + 13 + 20 = 65`，与探针的 `slots 65 (nonempty 34, blank spacer 31)` 完全一致。
注意 **65 不是 9 的倍数** —— 因为最后一区之后不补行，这是正常的，不要拿「长度 % 9 == 0」当断言。

### 5.4 与参考实现（Aeronautics）的语义差异（**重要**）

两者的**记录值含义相反**，但落点是同一行。读懂这个差异，才不会在混用两套代码时错位：

| | 我们 | Aeronautics |
|---|---|---|
| 记录时机 | 加入本区物品**之前** | 计算完本区物品数**之后** |
| 记录单位 | **行**（`out.size() / 9`） | **行**（每区 `y += ceilDiv(物品数, 9) + 1`） |
| 记录值的含义 | **该分区首个物品所在行**（首区 = 1） | **该分区的横幅行**（首区 = 0） |
| 渲染用值 | `记录值 − 1` | `记录值 − 首个可见行`（直接用） |

依据（**读源码**）：`SimulatedCreativeTab.java` 的 `processItems` 里
`SECTION_Y_VALUES.put(id, y)` 之后紧跟 `y += Math.ceilDiv(itemCount, ITEMS_PER_ROW) + 1`，
`y` 初值为 0；而 `renderBanners` 里是 `int sectionRow = yValue - CURRENT_ROW;` 然后
`y = sectionRow * 18`（即**直接**把记录值当横幅行），配合 `padMenuItems` 开头
`addEmptySlots(padded, ITEMS_PER_ROW)` 补的那一整行 —— 首区横幅正好落在第 0 行。
文件绝对路径与抓取方式见 `05-参考来源与出处.md`。

**实践建议：** 不管记录的是哪一种语义，渲染端都用「自适应判定」去找那条空行
（`02-关键坑与对策.md` §4），这样两种语义都能兜住，而且永远不会把横幅画到物品上。

## 六、排序键：分区 → 金属 → 区内位次

同一个桶里的物品顺序也需要确定。我们的排序键是一个**打包成 `long` 的三元组**：

```java
public record Placement(Kind kind, int metalRank, int slot) {
    public long sortKey() {
        return ((long) this.kind.ordinal() << 32)   // 高 32 位：分区种类
             | ((long) this.metalRank       << 16)   // 中 16 位：金属位次
             | this.slot;                            // 低 16 位：区内位次
    }
}
```

排序键 = **（分区序号，金属序号，区内序号）**，三个字段都是小整数，位宽足够（金属 ≤ 65535、区内 ≤ 65535）。

- **金属位次**：在唯一一张有序表（`METAL_ORDER`）里查下标；**没列进来的金属排最后**
  （`metalRank()` 返回 `METAL_ORDER.size()`）。这是「以后会加很多金属」的关键设计：
  新金属忘了登记也只会排到最后，不会丢、不会崩。
- **区内位次**：按后缀查表（§7.2）。例：金属材料区 = 核心材料 0 / 原料 1 / 锭 2 / 粒 3 / 模板 4。

**桶内排列的实际顺序是「非金属在前、金属在后」**：分桶时把不能分类的物品直接按投放顺序进 `plain` 列表，
认得出 `Placement` 的进 `metals` 列表并按 `sortKey` 排序，最后 `bucket = plain + sorted(metals)`
（`CreativeTabSections.java:55-58`）。这是有意的：非金属物品（例：礼品盒）保持注册顺序最容易预期；
金属物品则严格按「金属顺序 + 部位顺序」排，一目了然。如果你的设计希望金属优先，把两段对调即可，
但**要改就只改这一处**。

唯一例外是**显式声明了桶内比较器的 `Slot`**：本仓库目前只有建筑方块页的「其他建筑方块」（传
`CreativeSections.SUITE_ORDER`），它整桶按「建材类型位次 → 物品 id」重排 —— 普通金那套建材因此也按
砖块 → 柱 → 楼梯 → 台阶 → 墙 → 门 → 活板门 → 栏杆 → 链 → 灯笼 排，不属于任何套件的杂项（位次取「表长」）
排在全部套件之后。类型表仍是 `CreativeSections.BUILDING_SLOT` 那一张，与「金属建材」共用；其余分区一律走上面这条默认规则。

## 七、规则驱动：靠 id 后缀判定，**不枚举物品**

这是这套文档里最值钱的一条经验。假设你有 4 种金属、以后会有 16 种甚至更多：

- **绝对不要**为每种金属写一条横幅、一段 `if`、或一个物品清单。那是 O(金属数 × 部位数) 的代码量；
- 而是写成**规则**：物品注册名的**后缀**决定它属于哪个分区、区内第几位；
  **金属顺序只在唯一一处维护**。

### 7.1 单个物品 → `Placement` 的判定顺序

```
1. 没有任何金属前缀的「核心材料」（例：blazing_rod）→ 反查「金属 → 核心材料」表命中即归金属材料区，位次 0
2. 找出这个物品属于哪个金属（metalOf）
3. <金属>_block                     → 金属块区，位次 0
4. raw_<金属>                       → 金属材料区，位次 1
5. 后缀查 MATERIAL_SLOT 表          → 金属材料区（ingot 2 / nugget 3 / upgrade_template 4）
6. 后缀查 BUILDING_SLOT 表          → 金属建材区（bricks 0 … lantern 9）
7. 后缀查 GEAR_SLOT 表              → 金属装备区（sword 0 … boots 8）
8. 都不是                           → 返回 null
```

后缀表（节选自本仓库实际使用值）：

| 后缀 | 分区 | 区内位次 |
|---|---|---|
| 核心材料（每金属一个，随家族配置携带） | 金属材料 | 0 |
| `raw_<金属>` | 金属材料 | 1 |
| `<金属>_ingot` / `_nugget` / `_upgrade_template` | 金属材料 | 2 / 3 / 4 |
| `<金属>_block` | 金属块 | 0 |
| `<金属>_bricks` / `_pillar` / `_bricks_stairs` / `_bricks_slab` / `_bricks_wall` / `_door` / `_trapdoor` / `_bars` / `_chain` / `_lantern` | 金属建材 | 0…9 |
| `<金属>_sword` / `_axe` / `_pickaxe` / `_shovel` / `_hoe` / `_helmet` / `_chestplate` / `_leggings` / `_boots` | 金属装备 | 0…8 |

### 7.2 `metalOf` 的两个坑

1. **长 id 优先匹配。** 如果同时存在 `gold` 与 `sturdygold`，`sturdygold_ingot` 不能因为
   `startsWith("gold_")` 之类的判断而误判。我们的做法是遍历所有金属 id，取**命中的最长者**
   （`CreativeSections.metalOf`，`material\CreativeSections.java:103-113`）。
2. **前缀不能直接判定归属。** `path.startsWith(metal + "_")` 只对「金属 id 是整段前缀」的情况成立；
   `raw_<金属>` 的形式必须单独判。两者都要写，顺序无所谓，但**漏一个就会让物品掉进「其他」桶**
   （不会丢，但会跑到错的横幅下面）。

### 7.3 未知后缀怎么办：落到「其他」分区，**不丢**

`classify()` 认不出来就返回 `null`，调用方把它放进该页的兜底 `Slot`（通常是「其他材料」「其他工具」这种）。
这条规则的作用是：**任何新加的物品，哪怕你完全没写规则，也一定会出现在创造页的某个横幅下面**，
最坏情况是位置不理想，而不是「物品消失了」。这正是 §2 里「兜底判定放最后一位」的搭档。

### 7.4 金属清单的唯一来源

```java
public static final List<String> METAL_ORDER = List.of(
        "flamegold", "sturdygold", "voodoogold", "thundergold");   // 加金属 = 在这里加一行

public static List<String> allMetalIds() {        // 显式顺序 + 已注册但忘了登记的家族
    LinkedHashSet<String> ids = new LinkedHashSet<>(METAL_ORDER);
    for (MetalFamily family : MetalFamily.all()) ids.add(family.id);
    return List.copyOf(ids);
}
```

- **一个模组只需维护一张 `METAL_ORDER`**；`allMetalIds()` 再把「已经注册、但忘记写进表里」的金属补在后面，
  于是「忘记登记」的后果只是排序靠后。
- **核心材料建议直接由金属家族的配置携带**（例：`MetalFamily.Spec#coreItem`），
  这样「新金属一行配置」就自带核心材料，分区归属自动成立，不需要再维护第二张表。
- 核心材料没有金属前缀（`blazing_rod`），必须靠反查表命中；反查表可以在首次需要时**按需解析并缓存**
  （注意：注册期不能 `DeferredHolder.get()`，见 `02-关键坑与对策.md` §3 的姊妹坑）。

## 八、生成器与渲染之间的桥梁：长度守卫

生成器（`displayItems` 回调）里**只 accept 非空格子**，空行由 `getDisplayItems()` 补。
两边必须对得上，所以补之前要校验长度：

```java
Collection<ItemStack> padded(Collection<ItemStack> source) {
    List<Bucket> grouped = this.buckets;               // 生成时记下的分区结果
    if (grouped.isEmpty()) return source;

    List<ItemStack> flat = List.copyOf(source);
    int expected = grouped.stream().mapToInt(b -> b.items().size()).sum();
    if (expected != flat.size()) {
        // 有别的模组往本页插了物品（或删了物品）：宁可不画横幅，也不能错位
        return flat;
    }
    // 只按长度切片，物品本身以原版集合（= 真实内容）为准
    ... 重新构造 Bucket 后调用 layout()
}
```

为什么要切片而不是直接用自建列表：**`displayItems` 里可能已经被别人（`BuildCreativeModeTabContentsEvent`
的订阅者）插入过物品**。以原版集合为准 + 长度校验，是「不抢权、只在安全时加装饰」的态度。
长度对不上时**退回不加空行**，横幅自然也就不画（渲染端找不到空行），
效果是「退化成本来就有的普通创造页」，而不是错位或崩溃。

## 九、不变量清单（可以直接拿去做单元测试）

设第 b 个分区的物品数为 `n_b`、`SECTION_ROWS` 记录的值为 `R_b`（0 基行号），
`P = 9`（每行格数）、`B` = 分区数：

| 编号 | 不变量 | 用途 |
|---|---|---|
| **I1** | `R_0 == 1`（每页第一个分区的记录值恒为 1） | 检测「开头补行」是否被误删 |
| **I2** | `R_b − 1` 那一行**整行都是空格子** | 横幅安全绘制的前提，**渲染端唯一依赖的不变量** |
| **I3** | `Σ n_b == 候选物品数 == 非空格子数 == 桶数统计出的物品总数`（三方相等） | 检测「物品被规则吃掉 / 重复放入」 |
| **I4** | `SECTION_ROWS` 在本页的键数 == 分区数 == 非空桶数 | 检测「释词重复导致记录互相覆盖」 |
| **I5** | 对任意可见行 `r`：第 `r` 行整行空 ⟺ `r` 是本页某个分区的横幅行 | 渲染端可用它反查释词（进阶做法） |
| **I6** | `R_{b+1} == ceil((R_b * P + n_b) / P) + 1` | 逐区自检 `layout()` 的算术 |

`R_{b+1} = ceil((R_b*9 + n_b)/9) + 1` 的推导：本区首物品行是 `R_b`，占了 `n_b` 个格子，
从 `R_b*9` 号格子开始放；放完后 `used = n_b % 9`，补 `(9-used)%9` 个格子收尾，
再空一整行 `9` 个格子，所以下一区首物品行 = `(R_b*9 + n_b + pad) / 9`，其中 `pad = (9-used)%9 + 9`。
用 `n_b = 9` 代入：`pad = 9`，下一行 = `(9*R_b + 9 + 9)/9 = R_b + 2` ✓（本区 1 行 + 空 1 行）。

> 想省事的话，**只需要 I2、I3 和 I6**：I2 保渲染不错位，I3 保不丢物品，I6 保行号算术正确。
> `04-验证清单.md` 给出了把这三条打成日志的具体做法。
