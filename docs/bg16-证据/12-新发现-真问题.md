## 一、【真 bug】闪耀藤条的「可堆肥 65%」**完全没生效**（数据地图命名空间写错）

| 项 | 内容 |
|---|---|
| 现象（A 级） | `ComposterBlock.getValue(new ItemStack(bettergold:glittering_vine))` = **`-1.0`**（= 「不是可堆肥物」的哨兵值，`ComposterBlock.java:488-493`）；`itemHolder().getData(NeoForgeDataMaps.COMPOSTABLES)` = **`null`** |
| 阳性对照（同一份探针、同一 tick） | 原版小麦 `ComposterBlock.getValue(new ItemStack(Items.WHEAT))` = **`0.65`**，`dataMapEntry=Compostable[chance=0.65, canVillagerCompost=false]` ⇒ **数据地图机制本身是好的**，只有这一条没进去 |
| 根因 | 数据地图的 id 由**文件路径的命名空间**决定：`data/<ns>/data_maps/<registry>/<path>.json` ⇒ `<ns>:<path>`。NeoForge 内置的表是 **`neoforge:compostables`**（`NeoForgeDataMaps.COMPOSTABLES = DataMapType.builder(id("compostables"), …)`，`id(...)` 用 `neoforge` 命名空间；jar 内真实文件 = **`data/neoforge/data_maps/item/compostables.json`**）。本项目把它写在 **`src/main/resources/data/bettergold/data_maps/item/compostables.json`** ⇒ 注册出来的是 **`bettergold:compostables`**（一个**从未注册过**的数据地图类型）⇒ **静默丢弃**：不报错、不崩、`runData` 与五个校验器全绿，只是那 65% 永远读不到 |
| 代码/文档自相矛盾（同一处的证据） | `material/MetalSpecialItems.java:50-53` 的 javadoc 写的是「走 `neoforge:compostables`（`data/bettergold/data_maps/item/compostables.json`）」——**把两个不同的命名空间写在同一句里** |
| 影响 | 1.6 新物品 `glittering_vine` 在堆肥桶里**完全没有反应**（既不加层也不消耗的判定为 0/负值） |
| 修法（**未执行，等作者裁定**） | 把文件移到 `src/main/resources/data/neoforge/data_maps/item/compostables.json`（内容不变）；或在生成器里产出到 `data/neoforge/...`。⚠ 若作者更希望它只在本模组的表里生效，那要**先注册** `bettergold:compostables` 并把 `ComposterBlock` 的读取点换掉（原版读的是 `neoforge:` 那张，不注册就等于现在这样） |
| 证据 | `docs/bg16-证据/09-A级-runServer世界行为-读数.txt` 的 `compost_probe` / `compost_vanilla_control_is_loaded` / `compost_glittering_vine_0p65` 三行 |

> 一句话：**数据地图的命名空间是 id 的一部分**，写错 = 静默无效（和「标签目录写成复数」「物品标签里写了方块 id」是同一族）。

## 二、【口径偏差】金属弩的**实际蓄力是 25 tick**，不是规格写的 20 tick

| 项 | 内容 |
|---|---|
| A 级读数（真玩家按住右键不放，逐 tick 采样） | `chargeDuration=20 useDuration=23 vanillaChargeDuration=25`；按住期间 `CHARGED_PROJECTILES` **恒空**（`charged=false`），`useItemRemaining` 从 22 一路走到 **−14**（`usingItem` 一直 true）；**松手那一 tick** `charged=true` |
| 机理（读源码） | 原版「装满」判定在 `CrossbowItem#releaseUsing`：`i = getUseDuration(stack, entity) - timeLeft`，`f = getPowerForTime(i, stack, entity) = i / CrossbowItem.getChargeDuration(stack, entity)`，要求 `f >= 1.0F`。这里 **`getChargeDuration` 是 `static`**（`CrossbowItem.java:257-260`，基础 1.25F×20 = **25**）⇒ **改 `getUseDuration` 不会让分母跟着变**：`f_max = 23/25 = 0.92 < 1`（这正是 `MetalWeapons.MetalCrossbowItem` 类注释里「两个 i 都来自同一个 getUseDuration，所以只要它变小、比值自动仍是 1.0」那句**推断不成立**的地方）。玩家按住超过 `getUseDuration`(23) 之后 `useItemRemaining` 转负、松手时 `i = 实际按住 tick 数` ⇒ 真正装满需要 **≥25 tick**（本项目规格写的是 **20 tick**） |
| 影响 | ① 手感比规格慢 5 tick（0.25 s）；② **不是功能坏**——本项目自己的 `chargeDuration()`(20) 只被 `getUseDuration` 与**客户端拉弓谓词**用到，服务端装载判定仍走原版 25 |
| 顺带记一条**A 级反例（前一轮我自己的错误结论）** | 用 `ServerPlayer#startUsingItem` **服务端手工**开弩，客户端并不认为在「使用中」，下一次位置/动作包就把它 `stopUsingItem` 掉（读数：`t3 remaining=22 → t4 usingItem=false remaining=0`），于是松手时 `i=23`、`f=0.92`、**永远装不上** ⇒ 当时我判成「弩彻底不能用」。改成**客户端真实按键**驱动后一次就复现了正常行为（`after_release:charged=true`）。**结论：物品「使用中」状态是客户端权威的，服务端手工 `startUsingItem` 会被客户端覆盖**，用它测「按住类」行为必然得到假红 |
| 证据 | `docs/bg16-证据/10-A级-runClient读数.txt` 的 `crossbow_ready` / `crossbow_sample_t5..t40` / `crossbow_sample_after_release` 三段 |

> **需要作者一句话裁定**：是把「20 tick」当规格去修（那就必须**同时**覆写装载判定的比较基线，不能只改 `getUseDuration`），
> 还是把规格改成「与原版一致的 25 tick、按住的实现方式改为松手装载」。
