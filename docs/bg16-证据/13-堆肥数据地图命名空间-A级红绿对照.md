**为什么只改这一处**：`ComposterBlock#getValue`（`ComposterBlock.java:488-492`，neoforge sources）唯一的读取点是

⇒ 文件必须落在 `data/neoforge/data_maps/item/`。原位置注册出来的是**从未注册过**的 `bettergold:compostables`，**整条被丢弃**。

### 2.2 判据的说明（每一行都可复算）

| 断言 | 判据 | 读到的值 |
|---|---|---|
| `compost_map_id_is_neoforge` | 读取点用的那张表**就是** `neoforge:compostables` | `NeoForgeDataMaps.COMPOSTABLES.id()` = `neoforge:compostables` |
| `compost_vine_getValue_0p65`（**本条的真 bug**） | `ComposterBlock.getValue(new ItemStack(glittering_vine))` | 改前 **−1.0** ⇒ 改后 **0.65** |
| `compost_vine_datamap_not_null` | `stack.getItemHolder().getData(NeoForgeDataMaps.COMPOSTABLES)` | 改前 **null** ⇒ 改后 `Compostable[chance=0.65, canVillagerCompost=false]` |
| **阳性对照** `compost_vanilla_wheat_control` | 原版小麦（同一张表里的既有条目） | 两轮都 `0.65` + 条目非空 |
| **阳性对照 ②** `compost_vanilla_seeds_control_0p3` | 原版小麦种子（**值不同** ⇒ 证明读数是逐条读出来的，不是常量） | 两轮都 `0.3` |
| **阴性对照** `compost_negative_stone` | 原版石头（不可堆肥） | 两轮都 `−1.0` + 条目 `null` |
| **阴性对照 ②** `compost_negative_own_shard` | 本模组自己的 `bundled_echo_shard`（不可堆肥） | 两轮都 `−1.0`（**范围不外溢**） |
| **真世界端到端** `..._insert_vine_levels_up` | 真堆肥桶方块：`level 0 --ComposterBlock.insertItem(...)--> ?` | 改前 **0**（没反应）⇒ 改后 **1** |
| 端到端阳性/阴性 | 小麦 ⇒ 1；石头 ⇒ 0 且**堆栈不消耗**；`bundled_echo_shard` ⇒ 0 且 `stackLeft=1` | 两轮一致 |

> 端到端为什么是**确定性**的：`ComposterBlock#addItem`（`:304-320`）的判定是
> `if ((i != 0 || !(f > 0.0F)) && !(random.nextDouble() < f)) return state;`
> ⇒ **level 0 且 `getValue > 0` 时第一层必定成功**（不看随机数）。所以「level 0 插一次 ⇒ 1」是精确断言，
> 不是统计抽样；而 `insertItem`（`:273-282`）在 `getValue > 0` 不成立时**连堆栈都不消耗**（也逐条断言了）。

## 三、同类扫描：「写成 `bettergold:` 但实际该属 `neoforge:` / `c:` / `minecraft:`」的数据地图与标签
